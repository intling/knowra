知寻 knowra — 混合检索方案设计

向量语义检索（pgvector HNSW） + 关键词检索（PostgreSQL tsvector + ts_rank_cd）→ RRF 融合
📅 2026-08-12 📋 暂不实现：独立 Recall 阶段、精排 Reranker 🔗 依赖：QueryRewriter（已有）→ 用户问题向量化（已有）；向量语义检索（HNSW）与关键词检索均为本次新增

1. 动机与目标

1.1 当前状态

knowra 当前检索管线为纯向量语义检索：用户查询经 QueryRewriter 优化后（如已配置）→ EmbeddingAdapter 向量化 → pgvector cosine_distance 全表扫描（尚无向量索引，HNSW 索引为本次方案新增）→ Top-K 分块 → LLM 生成回答。

痛点：纯向量检索对专有名词、缩写、代码标识符、精确术语匹配存在天然劣势——向量的语义压缩会丢失精确的词汇信号，导致"术语 A"被语义相似的"术语 B"置换。

1.2 目标

本方案并非"不改动现有向量检索路径"——现有向量检索为 pgvector cosine_distance 全表扫描（无索引），基于 HNSW 的向量语义检索尚未实现。因此本方案同时：① 新增 pgvector HNSW 向量索引（向量检索从全表扫描升级为近似最近邻，见 §3.0）；② 新增关键词检索（tsvector + ts_rank_cd）作为第二通路；③ 通过 RRF（Reciprocal Rank Fusion）融合双路结果，弥补向量检索对精确关键词匹配的盲区。

目标描述优先级
向量语义检索（HNSW）在已有 embedding_vector 列上新建 HNSW 索引，cosine_distance 全表扫描 → 近似最近邻P0
双路并行召回向量语义 + 关键词检索同时触发（各自独立 Session，经线程池并行 I/O）P0
RRF 融合无超参融合双路结果，输出统一 Top-KP0
中文分词Jieba 分词 + PG tsvector GIN 索引，支持中英混合P0
关键词索引构建分块完成后立即构建（与分块同源）P0
优雅降级关键词通路不可用时自动回退纯向量检索P0
无缝集成SearchService 内部双路合并，对外 API 不变P0

1.3 非目标（明确排除）

  • 独立的粗召回（Recall）阶段 —— 双路检索即为召回阶段
  • 精排 Reranker（如 ColBERT、BGE-Reranker、Cross-Encoder）—— 后续迭代引入
  • 知识图谱辅助检索
  • 外部搜索引擎（Elasticsearch / Meilisearch）

关键设计决策：两步检索在同一请求内并行召回——向量与关键词两路 同时触发，各自由独立 Session（线程内新建/绑定）执行，绝不跨线程共享。 实现机制：用 asyncio.to_thread()（底层 loop.run_in_executor）把两路同步 检索分别调度到默认线程池的独立线程，再 asyncio.gather 汇总——这是真实并行， 两路 DB I/O 等待时间相互重叠，端到端延迟由「两路之和」降为「两路中较慢者」。

修正说明：旧版称「asyncio.gather 包裹同步 DB 调用是伪并发」——该结论仅在 同步函数直接在协程里被调用（阻塞事件循环、串行排队）时成立。改用 asyncio.to_thread 后，每个同步调用都在独立 OS 线程中执行，I/O 等待天然并行，伪并发的前提已被消除。 向量化与分词分别并入对应线程，避免额外的上下文切换开销。

3. 组件设计

3.0 向量语义检索 扩展：HNSW 索引

backend/app/services/search.py — SearchService._vector_search()

现状澄清：向量语义检索并非全新通路——DocumentEmbedding.embedding_vector （vector(2560)）与 cosine_distance 精确检索已存在， 但当前为全表扫描（无 ANN 索引，README 亦标注 "no ANN index yet"）。 本方案新增 pgvector HNSW 近似最近邻索引，检索复杂度从 O(N) 降为 O(log N)。 因此向量通路在本方案中从"已有不动"修正为"扩展"：检索语义 （cosine_distance 越小越相似）与对外 API 不变，仅新增索引层 + 候选池放大 + ef_search 调参。

检索实现（现状精确扫描 → 扩展为 HNSW 近似最近邻）

# search.py — _vector_search()：现状为全表扫描，扩展后走 HNSW 索引 + 候选池放大 def _vector_search(self, query_vector: list[float], candidate_pool: int): """pgvector cosine-distance 向量检索（HNSW 近似最近邻）。 相比现状的三处扩展： 1. HNSW 索引（§4.0）——建在 document_embeddings.embedding_vector 上， PostgreSQL 对 `ORDER BY distance LIMIT n` 自动走 ANN 索引， SQL 主体不变，检索从全表扫描 O(N) 变为近似最近邻 O(log N)。 2. ef_search 会话配置——检索前 `SET LOCAL hnsw.ef_search = :ef`， 控制召回率/延迟权衡（默认 40，建议 50-200，见 §4.0）。 3. candidate_pool——LIMIT 由 top_k 放大为 top_k × multiplier， 为 RRF 融合预留候选（§5.1 / §6）。 """ # 会话级 ef_search：仅本次事务生效，不影响其他并发检索 self._session.execute( sa_text("SET LOCAL hnsw.ef_search = :ef"), {"ef": self._settings.hnsw_ef_search}, ) distance_expr = DocumentEmbedding.embedding_vector.cosine_distance(query_vector) stmt = ( select( DocumentEmbedding, DocumentChunk, ParsedDocument, UploadedFile.original_filename.label("document_name"), distance_expr.label("score"), ) .join(DocumentChunk, DocumentEmbedding.chunk_id == DocumentChunk.id) .join( ParsedDocument, DocumentEmbedding.parsed_document_id == ParsedDocument.id, ) .join( UploadedFile, ParsedDocument.uploaded_file_id == UploadedFile.id, ) .where(UploadedFile.deleted_at.is_(None)) .order_by(distance_expr.asc()) .limit(candidate_pool) # 由 top_k 放大（现状为 limit(top_k)） ) return self._session.exec(stmt).all()
属性值
向量列document_embeddings.embedding_vector，vector(2560)（已存在，见 DocumentEmbedding 模型）
索引HNSW（vector_cosine_ops），m=16 / ef_construction=200（本次新增，见 §4.0）
检索算子cosine_distance（越小越相似），与现状一致，语义不变
查询时调参SET LOCAL hnsw.ef_search 会话级配置（默认 100），召回率/延迟权衡
候选池top_k × vector_search_top_k_multiplier（默认 ×2），供 RRF 融合
过滤排除软删除文件（UploadedFile.deleted_at IS NULL）；similarity_threshold / min_score_threshold 为通路内门（§7.2）
为什么"向量通路"必须从"已有不动"改为"扩展"？
混合检索的前提是双路都能高效、稳定地产出候选。若向量通路仍停留在 O(N) 全表扫描， 则「向量 + 关键词 + RRF」的总延迟会随知识库增长线性恶化，混合检索的收益会被扫描开销吃掉。 因此 HNSW 索引不是可选的性能优化，而是混合检索 P0 目标的前置依赖—— 它让向量通路在放大候选池（×2）的同时，检索延迟反而下降一个量级（§9.1）。

3.1 Jieba 分词器 新模块

backend/app/services/tokenizer.py

轻量封装 Jieba 分词，负责将中文文本转换为空格分隔的 token 序列，供 PostgreSQL to_tsvector 消费。

# tokenizer.py — Jieba 分词器封装（不可变快照 + 写时复制） import jieba class ChineseTokenizer: """中英混合文本分词器，输出空格连接的 token 序列。 PostgreSQL tsvector 原生不支持中文分词（仅按单字处理）， 因此需要应用层分词后再写入 tsvector 列。 并发模型：每个实例持有一个**不可变分词器快照**（独立的 jieba.Tokenizer 实例），构造后**冻结**——绝不调用 add_word / suggest_freq / del_word 等可变接口。词典更新走**写时复制**： 基于旧快照重建一个新的 Tokenizer 并原子替换引用，正在进行的 分词不受影响。这保证跨 uvicorn 多 worker 的 token 边界一致， 避免运行时改词典导致的读写竞争与索引/查询 tokenizer 漂移。 """ def __init__(self, user_dict: str | None = None): """初始化：加载词典并冻结为不可变快照。""" self._tokenizer = jieba.Tokenizer() # 独立实例，非模块级全局 if user_dict: self._tokenizer.load_userdict(user_dict) self._freeze() # 构造完成后禁止任何词典变更 def _freeze(self) -> None: """冻结快照：此后调用 add_word 等一律拒绝（防御性断言）。""" self._frozen = True def _assert_not_frozen(self) -> None: if self._frozen: raise RuntimeError( "ChineseTokenizer 为不可变快照，禁止运行时改词典；" "如需更新请走写时复制的 reload()" ) def reload(self, user_dict: str | None = None) -> None: """写时复制：重建快照并原子替换，供词典热更新使用。""" new_tokenizer = jieba.Tokenizer() if user_dict: new_tokenizer.load_userdict(user_dict) self._tokenizer = new_tokenizer # 原子替换引用 def tokenize(self, text: str) -> str: """分词并返回空格连接的 token 字符串（索引端·精确模式）。 示例: "大模型在医疗领域的应用" → "大 模型 在 医疗 领域 的 应用" """ if not text or not text.strip(): return "" tokens = self._tokenizer.cut(text.strip()) return " ".join(tokens)

3.2 关键词索引构建 集成点

在 backend/app/services/document_chunking.py 的 _run_job() 中，分块持久化成功后立即构建关键词索引。

触发时机

索引文本选择（与分块遍历同源 + setweight 四档权重）

关键词索引必须在分块阶段的同一遍历内、用chunker 刚吐出的内存 chunk 对象构建——在 _save_chunk 拿到 stored.text 之前直接读取内存中的 chunk.text / contextualized_text / heading_path。绝不读落库后的 DocumentChunk 字段，也绝不碰 *_storage_key——超限分块落库后 text/contextualized_text 已是 NULL（正文被卸载到磁盘），读它们是多余且易漂移的二次路径。同时按字段重要性施加 setweight 四档权重区分字段贡献：

def _build_keyword_index_for_chunk( self, chunk, chunk_id, tokenizer: ChineseTokenizer ) -> None: """在 _save_chunk 持久化之后、用 chunker 原始内存 chunk 对象构建关键词索引。 输入改为 chunker 刚吐出的内存 chunk 对象，而非落库后的 DocumentChunk。落库后的 DocumentChunk.text 在正文 > inline_text_max_bytes （默认 2048 字节）时为 NULL——ChunkArtifactStorage._store_one 会把超限正文 写到磁盘并返回 (None, storage_key)。若读落库字段，恰是最该被索引的大分块 会被静默构建成空 tsvector。因此必须在这里、在 stored.text 之前，用内存 chunk.text/contextualized_text 分词，确保与向量化消费的是同一份权威原文。 评分改用 ts_rank_cd 后，调参面不再暴露 BM25 的 k1/b，转而 暴露 PG 原生 setweight 四档权重（A/B/C/D），按字段重要性加权拼接： A — 标题路径 heading_path（最高权重） B — contextualized_text（含标题路径与上下文摘要） C — 正文 text D — 保留（默认不启用） """ parts: list[tuple[str, str]] = [ (w, tokenizer.tokenize(text)) for w, text in ( ("A", " ".join(getattr(chunk, "heading_path", None) or [])), ("B", getattr(chunk, "contextualized_text", "") or ""), ("C", getattr(chunk, "text", "") or ""), ) if text and text.strip() ] if not parts: return # setweight(to_tsvector('simple', ...), weight) || ... 拼接为加权 tsvector。 # simple 配置避免英文词干化——分词已由 Jieba 完成，词边界已确定。 expr = " || ".join( f"setweight(to_tsvector('simple', :t{i}), '{w}')" for i, (w, _) in enumerate(parts) ) from sqlalchemy import text as sa_text self.session.execute( sa_text( "UPDATE document_chunks " f"SET keyword_search_vector = {expr} " "WHERE id = :chunk_id" ), {f"t{i}": t for i, (_, t) in enumerate(parts)} | {"chunk_id": chunk_id}, )
为什么「同源」必须落到「同一遍历 + 用 chunker 内存 chunk 对象 + 不碰 *_storage_key」？
若关键词通路在构建时读落库后的 contextualized_text/text 列、或经 *_storage_key 从对象存储取回正文，而向量化走的是另一条读取路径，则对象存储卸载开启后 两路内容会静默分叉——关键词索引到空/过时文本却无任何报错。Q11 的推荐解法是釜底抽薪： 在 _save_chunk 拿到 stored.text 之前、直接用 chunker 刚吐出的内存 chunk 对象构建——正文尚未卸载，*_storage_key 根本不参与，也就从根源上 消除了「关键词读列 / 向量读存储键」的分叉可能。

修正说明：原方案写"与向量化同源同遍历"，但向量化并不在分块遍历内—— 它由独立的 DocumentEmbeddingService 消费 document_embeddings 表完成。 因此准确表述应为：关键词索引与分块遍历同源（两者都在 _run_job 内消费同一份内存 chunk 字段）， 而非"与向量化同源"。
为什么暴露 setweight 四档权重、而非 BM25 的 k1/b？
既然评分函数已确定为 ts_rank_cd（并非 BM25），就不存在 k1/b 这类 BM25 专属的长度归一化 调参面——继续暴露 k1/b 只会让调参方向系统性跑偏。PG 原生的 setweight(tsvector, weight) 才是 ts_rank_cd 真实可用的排序调参面：A > B > C > D 四档权重按字段重要性加权后拼接进 tsvector，ts_rank_cd 会天然偏好高权重字段的命中（标题命中 > 上下文命中 > 正文命中）。 四档权重为固定字段映射（A 标题 / B 上下文 / C 正文 / D 保留），无需暴露为运行时可调参数。
为什么用 simple 配置而非 english？
simple 不做词干化（stemming）和停用词移除，因为 Jieba 已完成了分词， 词边界已确定。使用 english 会引入不必要的英文词干化，反而丢失信息。 对于关键词评分，simple 配合 Jieba 分词是最精确的组合。

3.3.1 plainto_tsquery 的 AND 语义陷阱 关键设计决策

问题：plainto_tsquery 的 AND 语义对中文查询是灾难性的。
plainto_tsquery('simple', '向量 语义 检索 如何 实现') 生成 '向量' & '语义' & '检索' & '如何' & '实现'——所有 5 个 token 必须同时出现在同一分块中，缺一不可。这在英文场景下或许可行（查询通常 2-5 个词），但 Jieba 搜索模式（cut_for_search）对 10 字中文查询可产出 8-15 个 token。每个 token 都是一个 AND 条件，任意一个 token 不在某分块中 → 该分块被排除。
概率分析：AND 语义有多容易零结果？

设单个 token 在任意分块中的出现概率为 p（典型值 0.15-0.35，取决于词汇通用性）。对于 n 个 token 的查询：

P(某分块匹配) = p₁ × p₂ × ... × pₙ ≈ pⁿ (假设独立同分布) n=5 (短查询): p=0.25 → P ≈ 0.25⁵ ≈ 0.098% 每 1000 chunks 约 1 个匹配 n=8 (中等查询): p=0.25 → P ≈ 0.25⁸ ≈ 0.0015% 每 1000 chunks 约 0.015 个匹配 n=12 (长查询): p=0.25 → P ≈ 0.25¹² ≈ 6×10⁻⁸ 基本不可能有匹配

在 knowra 的个人知识库场景（<10K chunks），5+ token 的 AND 查询大概率返回零结果。而 Jieba cut_for_search 的搜索模式必然产出 5+ token（子词切分策略），这意味着几乎所有中文查询都面临零结果风险。

实测推论：即使不做线上 A/B 测试，仅从概率分析即可得出——在一个 1000 chunks 的知识库中，token 数 ≥8 的中文查询用 AND 语义，零结果比例接近 100%。这与"5+ token"的经验阈值高度吻合。保守估计：30-50% 的中文查询在 AND 语义下关键词通路返回零结果。

为什么 OR + ts_rank_cd = "软 AND"？

这是关键洞察。切换到 OR 语义后，检索条件变得极其宽松——只要分块中包含任意一个查询 token 就能匹配。这解决了零结果问题，但也引入了一个新问题：会不会返回大量仅匹配单个无关 token 的噪声结果？

不会。原因有二：

  1. ts_rank_cd 是天然的排序器：PG 的 ts_rank_cd 基于 cover density（覆盖密度）计算分数。包含 5 个匹配 token 的分块分数远高于仅包含 1 个的分块。OR 语义下 ts_rank_cd 自动实现了"匹配越多 token 排名越高"的软 AND 效果。
  2. 候选池裁剪 + 相关性门：即使 OR 匹配了大量分块，只有候选池大小（top_k × multiplier）个最高分进入 RRF 融合；再叠加 §3.3.2 的最少命中 token 门槛，把仅命中 1 个 token 的噪声结果直接过滤。低质量单 token 匹配不会污染最终结果。
查询: "向量语义检索的实现方案" Jieba cut_for_search → ["向量", "语义", "检索", "实现", "方案", "向量语义", "语义检索", "检索的", "实现方案"] 去重后 → 9 个独立 token AND (plainto_tsquery): '向量' & '语义' & '检索' & '实现' & '方案' & '向量语义' & '语义检索' & '检索的' & '实现方案' → 分块必须包含全部 9 个 token → 几乎必然零结果 OR (to_tsquery + |): '向量' | '语义' | '检索' | '实现' | '方案' | '向量语义' | '语义检索' | '检索的' | '实现方案' → 任意 token 命中即可匹配 → ts_rank_cd 按匹配密度排序 → 包含 "向量语义检索" 的分块（命中 3+ token）排在首位 → 仅含 "方案" 的分块排在末尾，被候选池截断 + 相关性门过滤
token 去重的必要性

Jieba cut_for_search 的搜索模式会产出包含子词切分的 token 列表。例如"向量化检索"切为 "向量" "量化" "向量化" "检索"，其中"向量化"已经作为完整 token 存在。如果不做去重：

  • 重复 token 增加 tsquery 表达式复杂度（虽不影响语义）
  • PG 的 GIN 索引对重复 token 的查询效率略低于去重版本

_build_or_tsquery 中的 set 去重 + list 保序策略在 O(n) 内完成，零额外开销。

安全性：SQL 注入防护

to_tsquery('simple', user_input) 本身是安全的——tsquery 解析器只识别 & | ! ( ) <-> 作为运算符，其他所有字符（包括 SQL 关键字、注释符、引号）都被当作普通词素处理。Jieba 分词产出的中文 token 不含 tsquery 运算符字符，因此直接拼接 | 是安全的。但为了防御性编程，如果将来支持英文混合查询，应对 token 做字面量转义或使用参数化查询（当前已用 :query 参数绑定）。

3.3.2 关键词通路的相关性门 关键设计决策

问题：ts_rank_cd + 候选池裁剪 不是"相关性门"。
排序函数只负责排序，LIMIT 只负责裁剪数量——二者都不能判定"这条结果是否相关"。 若查询经停用词过滤后仅剩 1 个高词频 token，关键词通路仍会返回大量仅命中该 token 的弱相关结果， 污染 RRF 融合。
两层相关性门（停用词过滤 + 最少命中 token 门槛）
门位置机制作用
停用词过滤 查询构造阶段（_build_or_tsquery） 显式停用词集合 _CHINESE_STOPWORDS 丢弃"的/如何/为什么"等无区分度虚词 从源头移除不贡献区分度的 token，避免它们计入"命中 token 数"
最少命中 token 门槛 结果过滤阶段（search 的 SQL） matched_terms >= min(2, meaningful_count)，统计每个分块命中的不同查询 token 数 多 token 查询丢弃仅命中 1 个 token 的弱相关结果；单 token 精确查询（缩写/专名）门槛自动降为 1，不被误杀
删除查询侧早退，结果侧门槛随查询长度自适应：
原设计在查询构造阶段有 if meaningful_count < min_token_match: return [] 的早退， 它把"单个高频泛词"（噪声）与"单个精确专名"（金信号）混为一谈——缩写/专有名词 （RAG/LLM/BERT/向量）分词后 meaningful_count=1， 被该早退一票否决，而这类查询恰是关键词通路相对向量检索最该补的盲区（§1.1）。 修正：删除查询侧早退；结果侧门槛改为 min(min_token_match, meaningful_count)。 停用词集合已挡掉"的/如何/为什么"等泛词，剩下来的单 token 是高精度精确匹配而非噪声。
这是一条"通路内门"，不是"整条管线的总闸"：
相关性门只作用于关键词通路内部。当关键词通路整路判空时，不导致整条搜索管线返回无结果—— 而是由向量通路独立兜底，最终在 RRF 融合后统一做 no-match 判定（见 §7.2）。 同理，向量通路自身的 similarity_threshold/min_score_threshold 也是通路内门， 与关键词通路互不干扰。
no-match 的最终裁判仍是余弦距离，而非"融合结果非空"：
关键词命中的分块可能是"包含该词、但语义离题"的块（例如一个含 RAG 却讲别的事的分块）， 而 OR 语义下关键词通路几乎必回非空——若以 fused 非空 判定 no-match，等于让关键词命中 绕过向量阈值、把幻觉风险原样放回。因此融合后的 no-match 判定锚定在 向量命中分块的最小 cosine_distance ≤ similarity_threshold：关键词命中只提升排名， 不单独制造相关；min_score_threshold 那道"最优分块仍太远→拒绝生成"的防线保留在向量侧。

3.4 RRF 融合 新模块

backend/app/services/search.py 内的私有方法 _rrf_fusion()

公式

1 1 RRF(d) = ───────────── + ───────────── + ... k + rank₁(d) k + rank₂(d) 其中: • d = 候选文档 (chunk) • rank_i = 文档在第 i 个检索器结果中的排名 (1-indexed) • k = 平滑常数，默认 60（学术界标准） 属性: • 免归一化：不同量纲的分数（cosine distance vs ts_rank_cd）无需归一化 • 单调性：排名越靠前的文档分数越高 • 多列表自然融合：同一文档出现在多个列表中时分数自动叠加

实现逻辑

from dataclasses import dataclass, replace from typing import Literal from uuid import UUID @dataclass class HybridCandidate: """统一中间契约—— 双路检索结果在融合前的唯一形态。 向量通路与关键词通路各自产出此契约，融合层只消费此契约， 不再感知来源差异。完整元数据在融合前补齐（见 §5.2）。 """ chunk_id: UUID source: Literal["vector", "keyword", "both"] # 来源标记（便于调试与加权扩展） vector_score: float | None = None # cosine_distance（越小越相似），仅向量通路有值 keyword_score: float | None = None # ts_rank_cd 分数，仅关键词通路有值 # 融合前补齐的完整元数据 parsed_document_id: UUID | None = None document_name: str = "" sequence_index: int = 0 text: str = "" contextualized_text: str = "" token_count: int | None = None heading_path: list[str] | None = None page_numbers: list[int] | None = None def _rrf_fusion( vector_candidates: list[HybridCandidate], keyword_candidates: list[HybridCandidate], *, rrf_k: int = 60, # RRF 平滑常数，独立参数 final_top_k: int, # 最终返回条数，单一真相（来自请求 top_k） ) -> list[HybridCandidate]: """RRF 融合向量检索与关键词检索结果。 两侧均为统一 HybridCandidate 契约，融合前已补齐元数据。 """ # 1. 构建每个检索器的 rank 映射: {chunk_id: rank}（1-indexed） vector_ranks = {c.chunk_id: i + 1 for i, c in enumerate(vector_candidates)} keyword_ranks = {c.chunk_id: i + 1 for i, c in enumerate(keyword_candidates)} # 2. 收集所有出现过的 chunk_id all_chunk_ids = set(vector_ranks) | set(keyword_ranks) # 3. 计算 RRF 分数 rrf_scores: dict[UUID, float] = {} for chunk_id in all_chunk_ids: score = 0.0 if chunk_id in vector_ranks: score += 1.0 / (rrf_k + vector_ranks[chunk_id]) if chunk_id in keyword_ranks: score += 1.0 / (rrf_k + keyword_ranks[chunk_id]) rrf_scores[chunk_id] = score # 4. 排序并取最终 top_k ordered = sorted(rrf_scores.items(), key=lambda kv: kv[1], reverse=True) top_ids = [cid for cid, _ in ordered[:final_top_k]] # 5. 合并双侧候选：同一 chunk 同时出现在两路时保留双侧分数（调试透明） merged: dict[UUID, HybridCandidate] = {} for c in vector_candidates: merged[c.chunk_id] = c for c in keyword_candidates: if c.chunk_id in merged: base = merged[c.chunk_id] merged[c.chunk_id] = replace( base, keyword_score=c.keyword_score, source="both", ) else: merged[c.chunk_id] = c return [merged[cid] for cid in top_ids]
性能考量：RRF 是纯计算操作，零 I/O、零网络调用，耗时通常 < 1ms。
三个显式参数：融合管线只认三处数字—— final_top_k（最终返回条数，来自请求 top_k）、 candidate_pool = top_k × multiplier（每路候选池大小，见 §5.1/§6）、 rrf_k = 60（RRF 平滑常数）。三者互不派生，消除"API=5 / keyword=10 / fusion=5"的多真相冲突。
RRF 如何做到「加权合并 + 去重、而非简单拼接」（需求 2）：
简单拼接（vector_top_k + keyword_top_k）会让两路结果各自保留原排名并列展开—— 不去重（同一 chunk 出现两次）、不全局重排（关键词弱相关结果直接插到向量强相关结果之前）， 造成噪声膨胀与无关结果插队。RRF 则：① 去重——以 chunk_id 为键合并两路，同一 chunk 只保留一条； ② 加权——每 chunk 的融合分 = 其在各路排名的倒数之和 Σ 1/(k+rankᵢ)，同时命中两路的 chunk 天然更高分； ③ 全局重排——按融合分排序后取 final_top_k，单路弱相关结果不会因「恰在另一路 top_k 之外」而插队。

层级机制触发时机说明
L0 · 运行时安全网 WHERE keyword_search_vector IS NOT NULL 每次关键词检索 NULL 分块自动跳过，仅参与向量检索路径，零用户影响
L1 · 机会性自愈 向量检索命中 NULL 分块时，通过有界并发队列异步回填关键词索引 检索时发现（fire-and-forget） 高频访问的分块自然完成回填，无需全量扫描；失败不影响检索结果。
并发安全设计：
① asyncio.Semaphore(3) 限制最多 3 个并发回填任务，防止高并发检索瞬间产生成百上千个回填任务挤占 CPU/DB 连接；
② 信号量耗尽时直接丢弃（不排队），因为回填是纯优化而非功能必需——排队只会堆积内存且延迟回填无意义；
③ 每个回填任务仅做 Jieba 分词（~1ms）+ 单条 UPDATE（~2ms），对正常检索路径的影响可忽略
L2 · 可观测性告警 服务启动时查询 NULL 比例，超过阈值（如 30%）记录 WARNING 日志 应用启动 / 健康检查 运维可感知存量缺口，决定是否触发全量回填
L3 · 批量回填命令 CLI 管理命令：分批处理 + 并行写入 + 进度上报 + 断点续传 运维手动触发 覆盖全量存量数据。
性能优化设计（注：关键词回填不需要 Embedding API，仅 Jieba 分词 + to_tsvector）：
① 批量 UPDATE：每批 500 条收集后，用一条多行 UPDATE … SET keyword_search_vector = CASE WHEN id=… THEN to_tsvector(…) … END 替代 500 次逐行 UPDATE，将 DB 往返从 O(N) 降为 O(N/500)；
② 并行 Worker：4 个 worker 各自独立读取→分词→攒批→写入，重叠 DB I/O 等待时间；
③ 预估吞吐：单条分词 ~1ms + 批量写入均摊 ~0.5ms/条 → 4 worker 理论 ~2.5K 条/秒；实际受 DB 写入带宽约束，保守预估 ~5K-10K 条/分钟；
④ 断点续传：每批次 commit 后记录最后处理的 chunk_id，中断后从此 ID 恢复，无需重跑已完成批次
L4 · 迁移时回填 Alembic 迁移提供 --backfill-existing 可选参数，在迁移中同步回填 部署迁移时（可选） 适合数据量小（<1K chunks）的场景，在迁移中一并完成

设计原则：L0 确保系统始终可用（无回填也能正常工作）；L1 让系统渐进式自愈（无需人工介入）；L2-L4 提供运维可控的加速路径。这是 AI 项目处理存量数据迁移的标准模式——宁可上线后再逐步完善，也不阻塞部署。

原方案令 score 保持余弦距离语义（非空 float），但混合检索允许 仅关键词命中的分块进入最终结果——这类分块从未进入向量通路，根本没有余弦距离， 非空 score 便无从取值。融合分数则不同：它是每个进入最终结果的分块都必然具备的值 （由 1/(k+rank) 单调映射而来），天然无空缺。

因此：① 融合后以 RRF 融合分数为唯一排序真相（score，越大越相关）； ② 原始双路分数降级为可选透传字段（vector_score / keyword_score）， 仅当分块出现在对应通路结果中时有值，仅用于调试与可视化，不参与排序。

⚠ 破坏性变更：score 的语义方向从"越小越相似"翻转为"越大越相关"，下游消费方需同步调整。 注意 no-match 判定等内部逻辑仍锚定在 vector_score（见 §7.2），不依赖 score。

10.1 已知风险

风险等级缓解措施
Jieba 分词精度不足：领域专有术语切分错误（如 "向量化" → "向量" + "化"） 中 六层递进式防御（详见 §10.3）：
L0 · 自定义词典 — TOKENIZER_USER_DICT_PATH 静态补充领域术语；
L1 · 动态词频调整 — jieba.suggest_freq() 无需词典文件即时纠正；
L2 · 自动术语发现 — 文档导入时基于 TF-IDF + C-value 自动提取候选术语加入词典；
L3 · 双模式分词 — 索引用精确模式、查询用搜索模式，提高召回；
L4 · N-gram 兜底 — 关键词结果过少时回退字符 bigram 检索；
L5 · QueryRewriter term_align 上游补偿（已有）
HNSW 近似精度损失：相比全表扫描，HNSW 是近似最近邻，可能漏掉少量真实最近邻 低 pgvector HNSW 在 <10K 向量规模下召回率接近 100%；ef_search 可动态调高换精度；检索后还有 RRF 融合与 LLM 生成补偿
ts_rank_cd 并非真正的 BM25：PG 的 ts_rank_cd 是 cover density（tf-idf 变体），与学术 BM25 有细微差异（缺 IDF 全局权重、无 k1/b 长度归一） 低 对检索质量影响可忽略；若后续需要精确 BM25，可迁移至 paradeDB/pg_search 扩展，接口不变
存量数据无索引：已上传文档的 keyword_search_vector 为 NULL 中 五层防御（详见 §4.1 存量数据处理）：
L0 · 运行时安全网 — NULL 分块自动跳过，仅参与向量检索；
L1 · 机会性自愈 — 有界并发（Semaphore(3) + 满即丢弃），检索命中时异步回填；
L2 · 可观测性 — 启动时 NULL 比例告警，运维可感知缺口；
L3 · 批量回填 CLI — 并行 Worker + 批量 UPDATE + 断点续传，无需 Embedding API；
L4 · 迁移时回填 — 小数据量场景迁移中一并完成。
关键原则：零阻塞部署 + 有界并发 — 存量不回填不影响正常工作，回填链路不冲击正常业务
双路并行增加 DB 连接占用：两个查询同时各占一个 session 低 两路并行执行且各自使用独立 Session——SQLAlchemy 同步 Session 非线程安全，绝不可跨线程共享；并行要求连接池空闲连接 ≥2（否则两路退化为排队等待），见 §2 修正说明
Jieba 分词速度：长文档分块可能耗时 低 仅在分块构建时执行一次（非检索路径）；可针对超长文本做截断保护

10.3 Jieba 分词精度 — 六层递进式缓解措施

Jieba 基于前缀词典 + HMM 的统计分词对通用文本效果良好，但对领域专有术语（如技术缩写、复合概念、中英混排词）存在系统性切分错误。以下六层措施按实施成本从低到高排列，每层独立可用、层层递进，形成纵深防御。

核心原则：分词精度问题无法根治——即使手工维护上千条词典，新术语仍会不断出现。缓解措施的目标是将影响降至可接受范围，而非追求 100% 正确分词。上述六层中 L0-L2 面向索引端（让 token 匹配正确），L3-L4 面向检索端（让查询命中即使分词不完美也能找到），L5 面向改写端（在进入分词前纠正查询表述）。三端协同比任何单点措施都更有效。

L0 · 自定义词典（静态补充）

最基础的缓解手段。通过 TOKENIZER_USER_DICT_PATH 环境变量指向一个纯文本词典文件，每行格式为 词语 词频 词性：

# tokenizer_user_dict.txt — 示例 向量化 100 n 大语言模型 200 n 知识图谱 150 n RAG 50 eng LLM 50 eng 零样本学习 80 n

使用方式：

  • 手动维护：根据业务领域预先整理常用术语列表，一次性写入词典文件
  • 增量追加：发现分词错误后追加新词，通过写时复制重建不可变快照生效（不依赖运行时 jieba.add_word() 修改全局词典）
  • 适用场景：术语数量 < 200 个、变更频率低的知识库
词频设置建议：词频越高，Jieba 越倾向将其作为整体切分。建议设为总词数×2（如总词数 50，设 100），使其优先级高于子词的组合概率。对于确定不应被切分的术语（如 "大语言模型"），可设更高值（如 200-500）。

L1 · 动态词频调整（无需词典文件）

在 backend/app/services/tokenizer.py 的 ChineseTokenizer.__init__() 中直接调用 Jieba API，无需额外词典文件。边界：L1 的 suggest_freq() 仅在 __init__() 构建不可变快照时执行一次，属快照构造的一部分；绝不在运行时（检索/导入路径中）调用，避免与 L2 的持久化快照产生冲突。

# tokenizer.py — 初始化时动态调整词频 import jieba class ChineseTokenizer: # 内置高频领域术语（可配置化） _BUILTIN_TERMS: list[str] = [ "向量化", "大语言模型", "知识图谱", "零样本", "注意力机制", "上下文窗口", "混合检索", ] def __init__(self, user_dict: str | None = None): if user_dict: jieba.load_userdict(user_dict) # 动态调整内置术语的词频，确保不被错误切分 for term in self._BUILTIN_TERMS: jieba.suggest_freq(term, tune=True) # 也可以调整个别词组的强制绑定 jieba.suggest_freq(("向量", "化"), tune=True) # 强制合并为 "向量化"
API效果适用场景
jieba.add_word(word, freq, tag)将词加入词典，后续分词永久生效确定需要作为一个整体切分的术语
jieba.suggest_freq(segment, tune=True)调整词频使指定切分更可能/更不可能纠正特定错误切分（如强制合并或拆分）
jieba.del_word(word)从词典中移除词某词被过度切分导致误匹配时

L2 · 自动术语发现（文档导入时提取）

这是最实用的长期方案——在文档分块完成后、构建关键词索引前，自动从文本中提取领域候选术语并加入 Jieba 词典。词典不可变快照 + 持久化为唯一真相，提取结果写入持久化 user_dict 文件，通过写时复制（copy-on-write）重建快照，避免各 worker 之间的词典漂移。

为什么推荐 TF-IDF + C-value 组合？
单独使用 TF-IDF 会提取大量"高频但不构成术语"的字串（如"的应用""是一个"）， 单独使用 C-value 在短文本上不稳定。两者结合：TF-IDF 提供候选池，C-value 过滤伪术语， 是 NLP 领域术语提取的经典廉价方案。对于 knowra 的个人知识库场景（<10K chunks）， 足以覆盖 80%+ 的领域术语。

L3 · 双模式分词（索引精确 + 查询宽泛）

Jieba 提供了两种分词模式。经典 IR 策略是索引端用精确模式、查询端用搜索模式——索引时 token 少而精（高精度），查询时 token 多而全（高召回），两者在 tsvector/tsquery 的 @@ 匹配中自然互补。

模式API效果示例（"向量化检索"）特点

查询端 搜索模式 jieba.cut_for_search(text) "向量" "量化" "向量化" "检索" token 多（含子词切分），tsquery 宽泛，提高召回
# keyword_search.py — 索引用精确、查询用搜索 class KeywordSearchService: def __init__(self, session, tokenizer): self._session = session self._tokenizer = tokenizer def search(self, query: str, top_k: int = 10) -> list[KeywordSearchResult]: # 查询端：搜索引擎模式（更细粒度 → 更高召回） tokenized = self._tokenizer.tokenize_for_search(query) # ... tsquery 匹配 ... # tokenizer.py — 提供两种分词接口 class ChineseTokenizer: def tokenize(self, text: str) -> str: """索引端：精确模式。用于写入 tsvector。""" return " ".join(jieba.cut(text.strip())) def tokenize_for_search(self, text: str) -> str: """查询端：搜索模式。用于构造 tsquery。""" return " ".join(jieba.cut_for_search(text.strip()))
效果分析：假设"向量化"未被词典覆盖，索引端精确模式切为 "向量" + "化"，查询端搜索模式切为 "向量" + "量化" + "向量化" + "检索"。 去重后用 |（OR）连接：'向量' | '量化' | '向量化' | '检索'。 索引中的 "向量" 命中查询中的 "向量"——即使"向量化"未被正确识别，查询仍能匹配到文档。 搜索模式自动提供了去重后的大量子词覆盖，OR 语义确保不会因单一 token 缺失而丢失匹配。 注意：如果使用 AND 语义（plainto_tsquery），"向量 & 量化 & 向量化 & 检索" 要求四个 token 同时存在， 在个人知识库中几乎必定零结果。这是采用 OR 语义的核心原因——详见 §3.3.1。

L4 · N-gram 兜底检索（最坏情况安全网）

当以上所有措施仍无法覆盖某个查询时（例如用户使用了全新的、Jieba 完全无法处理的术语），字符级 N-gram 是最可靠的兜底方案。它与 Jieba 分词完全正交——不依赖词典、不依赖语言模型。

OR 语义对 N-gram 触发频率的影响：采用 OR 语义后，主路径的零结果概率已趋近于零，N-gram 兜底的触发频率从原来的"< 5%"进一步降至 < 1%。 但 N-gram 兜底仍然保留——它应对的是 Jieba 分词完全失败（如纯符号查询、新造词）的极端情况，而非 AND 语义导致的假性零结果。
# keyword_search.py — 关键词结果不足时回退 N-gram（OR 语义下极少触发） class KeywordSearchService: # 阈值：关键词结果数低于此值时触发 N-gram 兜底 # OR 语义下此阈值极少被触发；设为 2 作为安全网 _MIN_KEYWORD_RESULTS = 2 def search(self, query: str, top_k: int = 10) -> list[KeywordSearchResult]: # 1. 主路径：Jieba 分词 → OR tsquery → ts_rank_cd 排序 tokenized = self._tokenizer.tokenize_for_search(query) results = self._keyword_search(tokenized, top_k) # 2. 兜底：结果过少时启用 N-gram（OR 语义下几乎不触发） if len(results) < self._MIN_KEYWORD_RESULTS: self._logger.info( "keyword_low_results_falling_back_to_ngram", keyword_count=len(results), query=query[:80], ) ngram_results = self._ngram_search(query, top_k) # 合并去重（N-gram 结果补充到关键词结果之后） existing_ids = {r.chunk_id for r in results} for nr in ngram_results: if nr.chunk_id not in existing_ids: results.append(nr) return results def _ngram_search(self, query: str, top_k: int) -> list[KeywordSearchResult]: """字符 bigram 检索：将查询按字符滑动窗口切分为 bigram， 作为独立 token 进行 OR tsquery 匹配。""" # "向量化" → ["向量", "量化"] (bigram) bigrams = [query[i:i+2] for i in range(len(query)-1)] if not bigrams: return [] tokenized = " ".join(bigrams) return self._keyword_search(tokenized, top_k)

索引端无需变更。N-gram 兜底复用现有 tsvector + GIN 索引，仅查询端生成 bigram token
得分N-gram 结果的 ts_rank_cd 评分天然低于精确匹配，排在关键词结果之后（符合预期）
误匹配风险低。2 字中文 bigram 的随机共现概率 ≈ 1/5000²，在知识库规模下几乎不产生噪音
触发频率预期 < 1% 查询触发（OR 语义下主路径已保证极高召回）。仅当关键词检索返回 < 2 条结果时激活

L5 · QueryRewriter term_align 上游补偿（已有）

QueryRewriter 的 term_align 策略在查询进入分词之前进行术语规范化——将口语化、简写、别称替换为标准术语。这从源头减少了 Jieba 遇到陌生表述的概率。

User Query: "向量化搜索怎么实现" │ ▼ QueryRewriter.term_align() └─ TermAlignmentLoader 加载 prompts/term_alignment.yaml └─ colloquial → formal 映射: "向量化搜索" → "向量语义检索" "怎么实现" → "如何实现" │ ▼ Rewritten: "向量语义检索如何实现" │ ▼ Jieba tokenize: "向量" "语义" "检索" "如何" "实现" ← 标准术语，分词正确

与 L0-L4 的协同关系：term_align 减少的是查询中的非标准表述（如 "大模型"→"大语言模型"），L0-L4 解决的是标准术语的切分精度问题。两者互补：term_align 让查询先"规范化"，L0-L4 确保规范化后的查询能被正确分词匹配。

term_align 的局限性：依赖 LLM 调用（有延迟和成本），且 vocabulary 需要手动维护。因此它在六层中处于 L5——有比没有好，但不能替代 L0-L4 的确定性措施。如果 query_rewrite_enabled=false（默认关闭），这一层完全不生效。

缓解效果汇总

基础前提：OR 语义查询构造（§3.3.1）。以下 L0-L5 六层解决的是"分词精度"问题（token 是否被正确切分）， 而 OR 语义解决的是更根本的"零结果"问题（token 如何组合成查询）。两者正交互补： L0-L5 确保 token 质量（术语被正确切分），OR + ts_rank_cd 确保查询不因 token 数量而失效（任何 token 命中即可贡献分数）。 没有 OR 语义，L0-L5 再完善也是徒劳——AND 逻辑会在 token 数达到阈值时数学上必然零结果。
