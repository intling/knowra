知寻 knowra — 混合检索方案设计

向量语义检索（pgvector HNSW） + BM25 关键词检索（ParadeDB pg_search）→ RRF 融合
📅 2026-08-12 📋 暂不实现：独立 Recall 阶段、精排 Reranker 🔗 依赖：QueryRewriter（已有）→ 用户问题向量化（已有）；向量语义检索（HNSW）与关键词检索均为本次新增

1. 动机与目标

1.1 当前状态

knowra 当前检索管线为纯向量语义检索：用户查询经 QueryRewriter 优化后（如已配置）→ EmbeddingAdapter 向量化 → pgvector cosine_distance 全表扫描（尚无向量索引，HNSW 索引为本次方案新增）→ Top-K 分块 → LLM 生成回答。

痛点：纯向量检索对专有名词、缩写、代码标识符、精确术语匹配存在天然劣势——向量的语义压缩会丢失精确的词汇信号，导致"术语 A"被语义相似的"术语 B"置换。

1.2 目标

本方案并非"不改动现有向量检索路径"——现有向量检索为 pgvector cosine_distance 全表扫描（无索引），基于 HNSW 的向量语义检索尚未实现。因此本方案同时：① 新增 pgvector HNSW 向量索引（向量检索从全表扫描升级为近似最近邻，见 §3.0）；② 新增 BM25 关键词检索（ParadeDB pg_search）作为第二通路；③ 通过 RRF（Reciprocal Rank Fusion）融合双路结果，弥补向量检索对精确关键词匹配的盲区。

目标描述优先级
向量语义检索（HNSW）在已有 embedding_vector 列上新建 HNSW 索引，cosine_distance 全表扫描 → 近似最近邻P0
双路并行召回向量语义 + 关键词检索同时触发（各自独立 Session，经线程池并行 I/O）P0
RRF 融合无超参融合双路结果，输出统一 Top-KP0
中文分词Jieba 分词 + ParadeDB pg_search BM25 索引，支持中英混合P0
关键词索引构建分块完成后立即构建（与分块同源）P0
优雅降级关键词通路不可用时自动回退纯向量检索P0
无缝集成SearchService 内部双路合并，对外 API 不变P0

1.3 非目标（明确排除）

  • 独立的粗召回（Recall）阶段 —— 双路检索即为召回阶段
  • 精排 Reranker（如 ColBERT、BGE-Reranker、Cross-Encoder）—— 后续迭代引入
  • 知识图谱辅助检索
  • 外部搜索引擎（Elasticsearch / Meilisearch）

关键设计决策：两步检索在同一请求内并行召回——向量与关键词两路 同时触发，各自由独立 Session（线程内新建/绑定）执行，绝不跨线程共享。 实现机制：用 asyncio.to_thread()（底层 loop.run_in_executor）把两路同步 检索分别调度到默认线程池的独立线程，再 asyncio.gather 汇总——这是真实并行， 两路 DB I/O 等待时间相互重叠，端到端延迟由「两路之和」降为「两路中较慢者」。

修正说明：旧版称「asyncio.gather 包裹同步 DB 调用是伪并发」——该结论仅在 同步函数直接在协程里被调用（阻塞事件循环、串行排队）时成立。改用 asyncio.to_thread 后，每个同步调用都在独立 OS 线程中执行，I/O 等待天然并行，伪并发的前提已被消除。 向量化与分词分别并入对应线程，避免额外的上下文切换开销。

3. 组件设计

3.0 向量语义检索 扩展：HNSW 索引

backend/app/services/search.py — SearchService._vector_search()

现状澄清：向量语义检索并非全新通路——DocumentEmbedding.embedding_vector （vector(2560)）与 cosine_distance 精确检索已存在， 但当前为全表扫描（无 ANN 索引，README 亦标注 "no ANN index yet"）。 本方案新增 pgvector HNSW 近似最近邻索引，检索复杂度从 O(N) 降为 O(log N)。 因此向量通路在本方案中从"已有不动"修正为"扩展"：检索语义 （cosine_distance 越小越相似）与对外 API 不变，仅新增索引层 + 候选池放大 + ef_search 调参。

检索实现（现状精确扫描 → 扩展为 HNSW 近似最近邻）

# search.py — _vector_search()：现状为全表扫描，扩展后走 HNSW 索引 + 候选池放大 def _vector_search( self, query_vector: list[float], candidate_pool: int, filters: RetrievalFilter, ): """pgvector cosine-distance HNSW 检索；先应用元数据范围过滤。""" 1. HNSW 索引（§4.0）——建在 document_embeddings.embedding_vector 上， PostgreSQL 对 `ORDER BY distance LIMIT n` 自动走 ANN 索引， SQL 主体不变，检索从全表扫描 O(N) 变为近似最近邻 O(log N)。 2. ef_search 会话配置——检索前 `SET LOCAL hnsw.ef_search = :ef`， 控制召回率/延迟权衡（默认 40，建议 50-200，见 §4.0）。 3. candidate_pool——LIMIT 由 top_k 放大为 top_k × multiplier， 为 RRF 融合预留候选（§5.1 / §6）。 4. filters——在 ANN 排序前添加时间/类型等结构化 WHERE 条件， 只在满足用户范围的集合内检索。 """ # 会话级 ef_search：仅本次事务生效，不影响其他并发检索 self._session.execute( sa_text("SET LOCAL hnsw.ef_search = :ef"), {"ef": self._settings.hnsw_ef_search}, ) distance_expr = DocumentEmbedding.embedding_vector.cosine_distance(query_vector) stmt = ( select( DocumentEmbedding, DocumentChunk, ParsedDocument, UploadedFile.original_filename.label("document_name"), distance_expr.label("vector_score"), ) .join(DocumentChunk, DocumentEmbedding.chunk_id == DocumentChunk.id) .join( ParsedDocument, DocumentEmbedding.parsed_document_id == ParsedDocument.id, ) .join( UploadedFile, ParsedDocument.uploaded_file_id == UploadedFile.id, ) ) stmt = apply_retrieval_filters(stmt, filters) stmt = stmt.order_by(distance_expr.asc()).limit(candidate_pool) # 由 top_k 放大（现状为 limit(top_k)） return self._session.exec(stmt).all()

为什么"向量通路"必须从"已有不动"改为"扩展"？
混合检索的前提是双路都能高效、稳定地产出候选。若向量通路仍停留在 O(N) 全表扫描， 则「向量 + 关键词 + RRF」的总延迟会随知识库增长线性恶化，混合检索的收益会被扫描开销吃掉。 因此 HNSW 索引不是可选的性能优化，而是混合检索 P0 目标的前置依赖—— 它让向量通路在放大候选池（×2）的同时，检索延迟反而下降一个量级（§9.1）。
元数据过滤必须先于 ANN/BM25 排序执行。 HNSW 与 pg_search 都只负责“在候选集合内找相似内容”，不能替代业务范围约束；检索请求应先由 QueryRewriter/FilterExtractor 产出结构化 RetrievalFilter，再把同一组参数下推到两路 SQL。这样“去年的财报”会被解析为报告类型=财报、时间范围=去年，而不是召回今年仅提到“去年”的文档。

3.0.1 统一元数据过滤（HNSW 与 pg_search 共享） P0

过滤条件由查询理解层生成，应用层只允许白名单字段和显式范围，不把自然语言直接拼进 SQL。过滤在两路检索中保持一致，避免一侧召回了被另一侧排除的文档，确保 RRF 的候选集合可比较。

@dataclass(frozen=True) class RetrievalFilter: """两路检索共享的结构化过滤条件；None 表示用户未提出该约束。""" created_at_from: datetime | None = None created_at_to: datetime | None = None # 半开区间 [from, to) document_types: tuple[str, ...] = () # pdf/docx/xlsx...（白名单） filename_patterns: tuple[str, ...] = () # 可选的受控类型/名称映射 # “去年的财报” → # RetrievalFilter(created_at_from=2025-01-01T00:00:00Z, # created_at_to=2026-01-01T00:00:00Z, # document_types=("financial_report",)) def apply_retrieval_filters(stmt, filters: RetrievalFilter): """对向量和关键词 stmt 复用同一套 WHERE 条件。""" stmt = stmt.where(UploadedFile.deleted_at.is_(None)) if filters.created_at_from is not None: stmt = stmt.where(UploadedFile.created_at >= filters.created_at_from) if filters.created_at_to is not None: stmt = stmt.where(UploadedFile.created_at < filters.created_at_to) if filters.document_types: stmt = stmt.where(UploadedFile.document_type.in_(filters.document_types)) return stmt
过滤字段映射需以真实 schema 为准。时间范围优先使用 uploaded_files.created_at；文档类型可使用已有结构化列或 metadata_json 中的白名单键（例如 source_format），不得用文件正文中的词命中来代替类型过滤。未能可靠解析的过滤条件应记录可观测性事件并采用“不过滤/询问用户”的显式策略，不能静默猜测。

3.1 Jieba 分词器 新模块

backend/app/services/tokenizer.py

轻量封装 Jieba 分词，负责将中文文本转换为空格分隔的 token 序列，供 ParadeDB pg_search BM25 索引消费。

# tokenizer.py — Jieba 分词器封装（不可变快照 + 写时复制） import jieba class ChineseTokenizer: """中英混合文本分词器，输出空格连接的 token 序列。 PostgreSQL BM25 索引 原生不支持中文分词（仅按单字处理）， 因此需要应用层分词后再写入 ParadeDB BM25 索引。 并发模型：每个实例持有一个**不可变分词器快照**（独立的 jieba.Tokenizer 实例），构造后**冻结**——绝不调用 add_word / suggest_freq / del_word 等可变接口。词典更新走**写时复制**： 基于旧快照重建一个新的 Tokenizer 并原子替换引用，正在进行的 分词不受影响。这保证跨 uvicorn 多 worker 的 token 边界一致， 避免运行时改词典导致的读写竞争与索引/查询 tokenizer 漂移。 """ def __init__(self, user_dict: str | None = None): """初始化：加载词典并冻结为不可变快照。""" self._tokenizer = jieba.Tokenizer() # 独立实例，非模块级全局 if user_dict: self._tokenizer.load_userdict(user_dict) self._freeze() # 构造完成后禁止任何词典变更 def _freeze(self) -> None: """冻结快照：此后调用 add_word 等一律拒绝（防御性断言）。""" self._frozen = True def _assert_not_frozen(self) -> None: if self._frozen: raise RuntimeError( "ChineseTokenizer 为不可变快照，禁止运行时改词典；" "如需更新请走写时复制的 reload()" ) def reload(self, user_dict: str | None = None) -> None: """写时复制：重建快照并原子替换，供词典热更新使用。""" new_tokenizer = jieba.Tokenizer() if user_dict: new_tokenizer.load_userdict(user_dict) self._tokenizer = new_tokenizer # 原子替换引用 def tokenize(self, text: str) -> str: """分词并返回空格连接的 token 字符串（索引端·精确模式）。 示例: "大模型在医疗领域的应用" → "大 模型 在 医疗 领域 的 应用" """ if not text or not text.strip(): return "" tokens = self._tokenizer.cut(text.strip()) return " ".join(tokens)

3.2 关键词索引构建 集成点

在 backend/app/services/document_chunking.py 的 _run_job() 中，分块持久化成功后立即构建关键词索引。

索引文本选择（与分块遍历同源 + 字段 boost）

关键词索引必须在分块阶段的同一遍历内、用chunker 刚吐出的内存 chunk 对象构建——在 _save_chunk 拿到 stored.text 之前直接读取内存中的 chunk.text / contextualized_text / heading_path。绝不读落库后的 DocumentChunk 字段，也绝不碰 *_storage_key——超限分块落库后正文可能为 NULL。同时将三个字段写入 ParadeDB BM25 索引的独立字段，通过字段 boost 区分标题、上下文与正文贡献：

def _build_keyword_index_for_chunk( self, chunk, chunk_id, tokenizer: ChineseTokenizer ) -> None: """在 _save_chunk 持久化之后、用 chunker 原始内存 chunk 对象构建关键词索引。 输入改为 chunker 刚吐出的内存 chunk 对象，而非落库后的 DocumentChunk。落库后的 DocumentChunk.text 在正文 > inline_text_max_bytes （默认 2048 字节）时为 NULL——ChunkArtifactStorage._store_one 会把超限正文 写到磁盘并返回 (None, storage_key)。若读落库字段，恰是最该被索引的大分块 会被静默构建成空 BM25 索引。因此必须在这里、在 stored.text 之前，用内存 chunk.text/contextualized_text 分词，确保与向量化消费的是同一份权威原文。 ParadeDB pg_search 的 BM25 索引使用独立字段保存标题、上下文和正文，并通过字段 boost 区分权重；k1/b 与长度归一化由 BM25 索引配置管理。 """ parts: list[tuple[str, str]] = [ (w, tokenizer.tokenize(text)) for w, text in ( ("A", " ".join(getattr(chunk, "heading_path", None) or [])), ("B", getattr(chunk, "contextualized_text", "") or ""), ("C", getattr(chunk, "text", "") or ""), ) if text and text.strip() ] if not parts: return # 将分词后的标题、上下文和正文分别写入 pg_search BM25 索引字段， # 字段 boost 在 ParadeDB BM25 索引配置中声明。 keyword_text = { "heading": parts.get("heading", ""), "context": parts.get("context", ""), "body": parts.get("body", ""), } self.session.execute( sa_text( "UPDATE document_chunks SET keyword_search_text = :keyword_text " "WHERE id = :chunk_id" ), {"keyword_text": keyword_text, "chunk_id": chunk_id}, )
为什么「同源」必须落到「同一遍历 + 用 chunker 内存 chunk 对象 + 不碰 *_storage_key」？
若关键词通路在构建时读落库后的 contextualized_text/text 列、或经 *_storage_key 从对象存储取回正文，而向量化走的是另一条读取路径，则对象存储卸载开启后 两路内容会静默分叉——关键词索引到空/过时文本却无任何报错。Q11 的推荐解法是釜底抽薪： 在 _save_chunk 拿到 stored.text 之前、直接用 chunker 刚吐出的内存 chunk 对象构建——正文尚未卸载，*_storage_key 根本不参与，也就从根源上 消除了「关键词读列 / 向量读存储键」的分叉可能。

修正说明：原方案写"与向量化同源同遍历"，但向量化并不在分块遍历内—— 它由独立的 DocumentEmbeddingService 消费 document_embeddings 表完成。 因此准确表述应为：关键词索引与分块遍历同源（两者都在 _run_job 内消费同一份内存 chunk 字段）， 而非"与向量化同源"。
ParadeDB BM25 参数与字段权重
ParadeDB pg_search 的 BM25 支持标准的 k1/b 长度归一化参数，并通过字段 boost 区分标题、上下文与正文权重。
为什么用 simple 配置而非 english？
simple 不做词干化（stemming）和停用词移除，因为 Jieba 已完成了分词， 词边界已确定。使用 english 会引入不必要的英文词干化，反而丢失信息。 对于关键词评分，simple 配合 Jieba 分词是最精确的组合。

3.3.1 ParadeDB pg_search 查询语义与 OR 方案 关键设计决策

应用层查询预处理：当前已通过 _CHINESE_STOPWORDS 停用词表过滤高频无意义词，再执行单字 Token 的字符类型检查。 为进一步降低低区分度噪声，建议在拼接 OR 查询前增加最小 Token 长度阈值 2：长度不足 2 的 单字 Token（包括单字标点、单个 ASCII 字母/数字）直接丢弃，长度为 2 及以上的中文术语、ASCII 缩写和数字标识符正常保留。 若业务必须支持单字专名，应通过白名单例外放行。具体落点为下方 _build_or_BM25 查询() 的规则 1-3（约第 677-711 行）。
问题：默认 AND 语义对中文查询是灾难性的。
plainpg_search query('simple', '向量 语义 检索 如何 实现') 生成 '向量' & '语义' & '检索' & '如何' & '实现'——所有 5 个 token 必须同时出现在同一分块中，缺一不可。这在英文场景下或许可行（查询通常 2-5 个词），但 Jieba 搜索模式（cut_for_search）对 10 字中文查询可产出 8-15 个 token。每个 token 都是一个 AND 条件，任意一个 token 不在某分块中 → 该分块被排除。
概率分析：AND 语义有多容易零结果？

设单个 token 在任意分块中的出现概率为 p（典型值 0.15-0.35，取决于词汇通用性）。对于 n 个 token 的查询：

P(某分块匹配) = p₁ × p₂ × ... × pₙ ≈ pⁿ (假设独立同分布) n=5 (短查询): p=0.25 → P ≈ 0.25⁵ ≈ 0.098% 每 1000 chunks 约 1 个匹配 n=8 (中等查询): p=0.25 → P ≈ 0.25⁸ ≈ 0.0015% 每 1000 chunks 约 0.015 个匹配 n=12 (长查询): p=0.25 → P ≈ 0.25¹² ≈ 6×10⁻⁸ 基本不可能有匹配

在 knowra 的个人知识库场景（<10K chunks），5+ token 的 AND 查询大概率返回零结果。而 Jieba cut_for_search 的搜索模式必然产出 5+ token（子词切分策略），这意味着几乎所有中文查询都面临零结果风险。

实测推论：即使不做线上 A/B 测试，仅从概率分析即可得出——在一个 1000 chunks 的知识库中，token 数 ≥8 的中文查询用 AND 语义，零结果比例接近 100%。这与"5+ token"的经验阈值高度吻合。保守估计：30-50% 的中文查询在 AND 语义下关键词通路返回零结果。

为什么 OR + BM25 = "软 AND"？

这是关键洞察。切换到 OR 语义后，检索条件变得极其宽松——只要分块中包含任意一个查询 token 就能匹配。这解决了零结果问题，但也引入了一个新问题：会不会返回大量仅匹配单个无关 token 的噪声结果？

不会。原因有二：

  1. BM25 是原生相关性排序器：ParadeDB pg_search 使用词频、逆文档频率和文档长度归一化计算分数。包含更多查询 token 的分块通常排名更高，OR 语义因此具备"软 AND"效果。
  2. 候选池裁剪 + 相关性门：即使 OR 匹配了大量分块，只有候选池大小（top_k × multiplier）个最高分进入 RRF 融合；再叠加 §3.3.2 的最少命中 token 门槛，把仅命中 1 个 token 的噪声结果直接过滤。低质量单 token 匹配不会污染最终结果。
查询: "向量语义检索的实现方案" Jieba cut_for_search → ["向量", "语义", "检索", "实现", "方案", "向量语义", "语义检索", "检索的", "实现方案"] 去重后 → 9 个独立 token OR (ParadeDB pg_search BM25): '向量' & '语义' & '检索' & '实现' & '方案' & '向量语义' & '语义检索' & '检索的' & '实现方案' → 分块必须包含全部 9 个 token → 几乎必然零结果 OR (pg_search query + |): '向量' | '语义' | '检索' | '实现' | '方案' | '向量语义' | '语义检索' | '检索的' | '实现方案' → 任意 token 命中即可匹配 → BM25 按匹配密度排序 → 包含 "向量语义检索" 的分块（命中 3+ token）排在首位 → 仅含 "方案" 的分块排在末尾，被候选池截断 + 相关性门过滤
token 去重的必要性

Jieba cut_for_search 的搜索模式会产出包含子词切分的 token 列表。例如"向量化检索"切为 "向量" "量化" "向量化" "检索"，其中"向量化"已经作为完整 token 存在。如果不做去重：

  • 重复 token 增加 BM25 查询 表达式复杂度（虽不影响语义）
  • PG 的 pg_search BM25 索引 索引对重复 token 的查询效率略低于去重版本

_build_or_BM25 查询 中的 set 去重 + list 保序策略在 O(n) 内完成，零额外开销。

安全性：SQL 注入防护

pg_search query('simple', user_input) 本身是安全的——BM25 查询 解析器只识别 & | ! ( ) <-> 作为运算符，其他所有字符（包括 SQL 关键字、注释符、引号）都被当作普通词素处理。Jieba 分词产出的中文 token 不含 BM25 查询 运算符字符，因此直接拼接 | 是安全的。但为了防御性编程，如果将来支持英文混合查询，应对 token 做字面量转义或使用参数化查询（当前已用 :query 参数绑定）。

3.3.2 关键词通路的相关性门 关键设计决策

问题：BM25 + 候选池裁剪 不是"相关性门"。
排序函数只负责排序，LIMIT 只负责裁剪数量——二者都不能判定"这条结果是否相关"。 若查询经停用词过滤后仅剩 1 个高词频 token，关键词通路仍会返回大量仅命中该 token 的弱相关结果， 污染 RRF 融合。
两层相关性门（停用词过滤 + 最少命中 token 门槛）
门位置机制作用
停用词过滤 查询构造阶段（_build_or_BM25 查询） 显式停用词集合 _CHINESE_STOPWORDS 丢弃"的/如何/为什么"等无区分度虚词 从源头移除不贡献区分度的 token，避免它们计入"命中 token 数"
最少命中 token 门槛 结果过滤阶段（search 的 SQL） matched_terms >= min(2, meaningful_count)，统计每个分块命中的不同查询 token 数 多 token 查询丢弃仅命中 1 个 token 的弱相关结果；单 token 精确查询（缩写/专名）门槛自动降为 1，不被误杀
删除查询侧早退，结果侧门槛随查询长度自适应：
原设计在查询构造阶段有 if meaningful_count < min_token_match: return [] 的早退， 它把"单个高频泛词"（噪声）与"单个精确专名"（金信号）混为一谈——缩写/专有名词 （RAG/LLM/BERT/向量）分词后 meaningful_count=1， 被该早退一票否决，而这类查询恰是关键词通路相对向量检索最该补的盲区（§1.1）。 修正：删除查询侧早退；结果侧门槛改为 min(min_token_match, meaningful_count)。 停用词集合已挡掉"的/如何/为什么"等泛词，剩下来的单 token 是高精度精确匹配而非噪声。
这是一条"通路内门"，不是"整条管线的总闸"：
相关性门只作用于关键词通路内部。当关键词通路整路判空时，不导致整条搜索管线返回无结果—— 而是由向量通路独立兜底，最终在 RRF 融合后统一做 no-match 判定（见 §7.2）。 同理，向量通路自身的 similarity_threshold/min_score_threshold 也是通路内门， 与关键词通路互不干扰。
no-match 的最终裁判采用“RRF 排序 + 最低证据门”，不再只依赖 vector_score：
rrf_score 只反映两路结果的排名贡献，适合确定最终顺序，但不是跨查询可比较的相关性概率，不能单独用固定值判空。 因此融合后先按 rrf_score 取 Top-K，再检查 Top-K 是否存在可靠证据：向量命中必须满足 vector_score ≤ similarity_threshold；仅关键词命中则必须同时满足关键词通路的最少命中 token 门槛和经评测校准的 keyword_score 下限。两者均不满足时才判定 no-match。这样保留向量阈值对幻觉的安全防线，也不会因 关键词结果没有 vector_score 而被误判为空；rrf_score 负责排序，原始分数负责证据校验，各自职责清晰。

3.4 RRF 融合 新模块

backend/app/services/search.py 内的私有方法 _rrf_fusion()

公式

w_vector w_keyword RRF(d) = ──────────────── + ──────────────── + ... k + rank_vector(d) k + rank_keyword(d) 其中: • d = 候选文档 (chunk) • rank_i = 文档在第 i 个检索器结果中的排名 (1-indexed) • w_i = 第 i 路排名权重（默认均为 1.0，即等权基线） • k = 平滑常数，默认 60（学术界标准） 当 w_vector = w_keyword = 1.0 时，公式退化为等权 RRF；权重只作用于排名贡献， 不应直接把未经校准的 cosine distance 与 BM25 原始分数相加。权重应通过离线标注集 或线上 A/B 验证后调整，并支持按查询意图覆盖。 属性: • 免归一化：不同量纲的分数（cosine distance vs BM25）无需归一化 • 单调性：排名越靠前的文档分数越高 • 多列表自然融合：同一文档出现在多个列表中时分数自动叠加

实现逻辑

2. 收集所有出现过的 chunk_id all_chunk_ids = set(vector_ranks) | set(keyword_ranks) # 3. 计算 RRF 融合分数（rrf_score） rrf_scores: dict[UUID, float] = {} for chunk_id in all_chunk_ids: rrf_score = 0.0 if chunk_id in vector_ranks: rrf_score += vector_weight / (rrf_k + vector_ranks[chunk_id]) if chunk_id in keyword_ranks: rrf_score += keyword_weight / (rrf_k + keyword_ranks[chunk_id]) rrf_scores[chunk_id] = rrf_score # 4. 排序并取最终 top_k ordered = sorted(rrf_scores.items(), key=lambda kv: kv[1], reverse=True) top_ids = [cid for cid, _ in ordered[:final_top_k]] # 5. 合并双侧候选：同一 chunk 同时出现在两路时保留双侧分数（调试透明） merged: dict[UUID, HybridCandidate] = {} for c in vector_candidates: merged[c.chunk_id] = c for c in keyword_candidates: if c.chunk_id in merged: base = merged[c.chunk_id] merged[c.chunk_id] = replace( base, keyword_score=c.keyword_score, source="both", ) else: merged[c.chunk_id] = c return [merged[cid] for cid in top_ids]
性能考量：RRF 是纯计算操作，零 I/O、零网络调用，耗时通常 < 1ms。
三个显式参数：融合管线只认三处数字—— final_top_k（最终返回条数，来自请求 top_k）、 candidate_pool = top_k × multiplier（每路候选池大小，见 §5.1/§6）、 rrf_k = 60（RRF 平滑常数）。三者互不派生，消除"API=5 / keyword=10 / fusion=5"的多真相冲突。
RRF 如何做到「加权合并 + 去重、而非简单拼接」（需求 2）：
简单拼接（vector_top_k + keyword_top_k）会让两路结果各自保留原排名并列展开—— 不去重（同一 chunk 出现两次）、不全局重排（关键词弱相关结果直接插到向量强相关结果之前）， 造成噪声膨胀与无关结果插队。RRF 则：① 去重——以 chunk_id 为键合并两路，同一 chunk 只保留一条； ② 加权——每 chunk 的融合分 = 其在各路排名的倒数之和 Σ 1/(k+rankᵢ)，同时命中两路的 chunk 天然更高分； ③ 全局重排——按融合分排序后取 final_top_k，单路弱相关结果不会因「恰在另一路 top_k 之外」而插队。

层级机制触发时机说明
L0 · 运行时安全网 WHERE keyword_search_text IS NOT NULL 每次关键词检索 NULL 分块自动跳过，仅参与向量检索路径，零用户影响
L1 · 机会性自愈 向量检索命中 NULL 分块时，通过有界并发队列异步回填关键词索引 检索时发现（fire-and-forget） 高频访问的分块自然完成回填，无需全量扫描；失败不影响检索结果。
并发安全设计：
① asyncio.Semaphore(3) 限制最多 3 个并发回填任务，防止高并发检索瞬间产生成百上千个回填任务挤占 CPU/DB 连接；
② 信号量耗尽时直接丢弃（不排队），因为回填是纯优化而非功能必需——排队只会堆积内存且延迟回填无意义；
③ 每个回填任务仅做 Jieba 分词（~1ms）+ 单条 UPDATE（~2ms），对正常检索路径的影响可忽略
L2 · 可观测性告警 服务启动时查询 NULL 比例，超过阈值（如 30%）记录 WARNING 日志 应用启动 / 健康检查 运维可感知存量缺口，决定是否触发全量回填
L3 · 批量回填命令 CLI 管理命令：分批处理 + 并行写入 + 进度上报 + 断点续传 运维手动触发 覆盖全量存量数据。
性能优化设计（注：关键词回填不需要 Embedding API，仅 Jieba 分词 + ParadeDB BM25 索引）：
① 批量 UPDATE：每批 500 条收集后，将分词后的字段对象批量写入 keyword_search_text，由 pg_search BM25 索引自动更新，减少 DB 往返；
② 并行 Worker：4 个 worker 各自独立读取→分词→攒批→写入，重叠 DB I/O 等待时间；
③ 预估吞吐：单条分词 ~1ms + 批量写入均摊 ~0.5ms/条 → 4 worker 理论 ~2.5K 条/秒；实际受 DB 写入带宽约束，保守预估 ~5K-10K 条/分钟；
④ 断点续传：每批次 commit 后记录最后处理的 chunk_id，中断后从此 ID 恢复，无需重跑已完成批次
L4 · 迁移时回填 Alembic 迁移提供 --backfill-existing 可选参数，在迁移中同步回填 部署迁移时（可选） 适合数据量小（<1K chunks）的场景，在迁移中一并完成

设计原则：L0 确保系统始终可用（无回填也能正常工作）；L1 让系统渐进式自愈（无需人工介入）；L2-L4 提供运维可控的加速路径。这是 AI 项目处理存量数据迁移的标准模式——宁可上线后再逐步完善，也不阻塞部署。

rrf_score 是 RRF 融合分数（越大越相关），不再复用含义含糊的 score。
原始余弦距离统一命名为 vector_score（非空 float），但混合检索允许 仅关键词命中的分块进入最终结果——这类分块从未进入向量通路，没有 vector_score。 因此融合分数不同：它是每个进入最终结果的分块都必然具备的值 （由 1/(k+rank) 单调映射而来），天然无空缺。

因此：① 融合后以 rrf_score 为唯一排序真相（越大越相关）； ② 原始双路分数统一使用可选字段（vector_score / keyword_score）， 仅当分块出现在对应通路结果中时有值，仅用于调试与可视化，不参与排序。

⚠ 破坏性变更：新增 rrf_score 替代原 score。为兼容已有前端或下游服务，建议短期保留 score 作为标记为 deprecated 的只读别名，并发布迁移通知；完成迁移后删除该别名。 no-match 判定等内部逻辑改为“证据门”：rrf_score 只负责融合后的排序，不作为固定阈值判空； vector_score 只校验向量证据，keyword_score 只校验已通过关键词通路相关性门的关键词证据。 这样既避免仅关键词结果绕过安全校验，也避免仅关键词命中因缺少 vector_score 被误判为 no-match。 详见 §7.2。

10.3 Jieba 分词精度 — 六层递进式缓解措施

Jieba 基于前缀词典 + HMM 的统计分词对通用文本效果良好，但对领域专有术语（如技术缩写、复合概念、中英混排词）存在系统性切分错误。以下六层措施按实施成本从低到高排列，每层独立可用、层层递进，形成纵深防御。

核心原则：分词精度问题无法根治——即使手工维护上千条词典，新术语仍会不断出现。缓解措施的目标是将影响降至可接受范围，而非追求 100% 正确分词。上述六层中 L0-L2 面向索引端（让 token 匹配正确），L3-L4 面向检索端（让查询命中即使分词不完美也能找到），L5 面向改写端（在进入分词前纠正查询表述）。三端协同比任何单点措施都更有效。

L0 · 自定义词典（静态补充）

最基础的缓解手段。通过 TOKENIZER_USER_DICT_PATH 环境变量指向一个纯文本词典文件，每行格式为 词语 词频 词性：

# tokenizer_user_dict.txt — 示例 向量化 100 n 大语言模型 200 n 知识图谱 150 n RAG 50 eng LLM 50 eng 零样本学习 80 n

使用方式：

  • 手动维护：根据业务领域预先整理常用术语列表，一次性写入词典文件
  • 增量追加：发现分词错误后追加新词，通过写时复制重建不可变快照生效（不依赖运行时 jieba.add_word() 修改全局词典）
  • 适用场景：术语数量 < 200 个、变更频率低的知识库
词频设置建议：词频越高，Jieba 越倾向将其作为整体切分。建议设为总词数×2（如总词数 50，设 100），使其优先级高于子词的组合概率。对于确定不应被切分的术语（如 "大语言模型"），可设更高值（如 200-500）。

L1 · 动态词频调整（无需词典文件）

在 backend/app/services/tokenizer.py 的 ChineseTokenizer.__init__() 中直接调用 Jieba API，无需额外词典文件。边界：L1 的 suggest_freq() 仅在 __init__() 构建不可变快照时执行一次，属快照构造的一部分；绝不在运行时（检索/导入路径中）调用，避免与 L2 的持久化快照产生冲突。

为什么推荐 TF-IDF + C-value 组合？
单独使用 TF-IDF 会提取大量"高频但不构成术语"的字串（如"的应用""是一个"）， 单独使用 C-value 在短文本上不稳定。两者结合：TF-IDF 提供候选池，C-value 过滤伪术语， 是 NLP 领域术语提取的经典廉价方案。对于 knowra 的个人知识库场景（<10K chunks）， 足以覆盖 80%+ 的领域术语。

L4 · N-gram 兜底检索（最坏情况安全网）

当以上所有措施仍无法覆盖某个查询时（例如用户使用了全新的、Jieba 完全无法处理的术语），字符级 N-gram 是最可靠的兜底方案。它与 Jieba 分词完全正交——不依赖词典、不依赖语言模型。

OR 语义对 N-gram 触发频率的影响：采用 OR 语义后，主路径的零结果概率已趋近于零，N-gram 兜底的触发频率从原来的"< 5%"进一步降至 < 1%。 但 N-gram 兜底仍然保留——它应对的是 Jieba 分词完全失败（如纯符号查询、新造词）的极端情况，而非 AND 语义导致的假性零结果。
# keyword_search.py — 关键词结果不足时回退 N-gram（OR 语义下极少触发） class KeywordSearchService: # 阈值：关键词结果数低于此值时触发 N-gram 兜底 # OR 语义下此阈值极少被触发；设为 2 作为安全网 _MIN_KEYWORD_RESULTS = 2 def search(self, query: str, top_k: int = 10) -> list[KeywordSearchResult]: # 1. 主路径：Jieba 分词 → OR BM25 查询 → BM25 排序 tokenized = self._tokenizer.tokenize_for_search(query) results = self._keyword_search(tokenized, top_k) # 2. 兜底：结果过少时启用 N-gram（OR 语义下几乎不触发） if len(results) < self._MIN_KEYWORD_RESULTS: self._logger.info( "keyword_low_results_falling_back_to_ngram", keyword_count=len(results), query=query[:80], ) ngram_results = self._ngram_search(query, top_k) # 合并去重（N-gram 结果补充到关键词结果之后） existing_ids = {r.chunk_id for r in results} for nr in ngram_results: if nr.chunk_id not in existing_ids: results.append(nr) return results def _ngram_search(self, query: str, top_k: int) -> list[KeywordSearchResult]: """字符 bigram 检索：将查询按字符滑动窗口切分为 bigram， 作为独立 token 进行 OR BM25 查询 匹配。""" # "向量化" → ["向量", "量化"] (bigram) bigrams = [query[i:i+2] for i in range(len(query)-1)] if not bigrams: return [] tokenized = " ".join(bigrams) return self._keyword_search(tokenized, top_k)

L5 · QueryRewriter term_align 上游补偿（已有）

QueryRewriter 的 term_align 策略在查询进入分词之前进行术语规范化——将口语化、简写、别称替换为标准术语。这从源头减少了 Jieba 遇到陌生表述的概率。

与 L0-L4 的协同关系：term_align 减少的是查询中的非标准表述（如 "大模型"→"大语言模型"），L0-L4 解决的是标准术语的切分精度问题。两者互补：term_align 让查询先"规范化"，L0-L4 确保规范化后的查询能被正确分词匹配。

term_align 的局限性：依赖 LLM 调用（有延迟和成本），且 vocabulary 需要手动维护。因此它在六层中处于 L5——有比没有好，但不能替代 L0-L4 的确定性措施。如果 query_rewrite_enabled=false（默认关闭），这一层完全不生效。

10.4 向量通路与关键词通路是否应等权融合？

结论先行：当前方案采用的是“等权 RRF 基线”，可行，但不应被视为最终最优权重。 §3.4 的实现对两个结果列表使用完全相同的贡献：1 / (rrf_k + rank)，且没有 w_vector / w_keyword 系数。因此它是按排名信号等权，不是把 cosine distance 与 BM25 原始分数直接相加；两种分数仍然没有被混合，等权的是两路的排名证据。

为什么作为第一版可行

  1. 避免分数不可比。 cosine distance 与 BM25 的量纲、方向和分布不同，直接做 α·vector_score + β·keyword_score 很容易因归一化、语料规模或查询长度变化而失真。 RRF 只依赖名次，天然绕开这一问题。
  2. 符合混合检索的常见工程基线。向量擅长语义改写和自然语言问题，BM25 擅长专名、缩写、数字、代码和精确短语；在没有标注数据时，让两路各自提供对称的证据，是低风险的冷启动策略。
  3. 对分词和模型漂移更稳健。某一路的绝对分数发生漂移时，不会像线性加权那样改变另一条通路的量级；同一 chunk 同时进入两路时会获得明确的交集奖励。
  4. 与当前小规模知识库匹配。knowra 预期规模小于 10K chunks，RRF 的 CPU 成本极低，能够先以统一指标上线，再用真实查询评测调整，而不是凭经验预设权重。

为什么“永久等权”并不充分

  • 用户查询具有不同意图：错误码、文件名、API、版本号、专有名词通常应提高关键词证据；解释概念、同义改写和自然语言问题通常更依赖向量证据。
  • 两路的召回质量可能不对称：HNSW 的 ef_search、中文分词质量、字段 boost、索引覆盖率和过滤条件都会改变某一路的可靠性。
  • RRF 的“同时命中奖励”并不等于相关性证明。当前 §7.2 规定关键词不能单独通过 no-match，这是安全的，但也意味着关键词通路目前主要是向量候选的排序增强；若产品目标是发现纯关键词命中，还需要独立的相关性校验或 reranker。
  • 候选池 ×2 可能过小。两路只取 top_k × 2 时，某一路的精确命中可能在另一条路的候选不足时无法进入融合；应通过召回率/延迟实验决定，常见起点可测试 ×5～×10，而不是固定假定 ×2。

推荐落地方案：等权冷启动 + 可配置加权 RRF

# 默认仍为等权，便于灰度、回滚和离线对比 weighted_rrf(d) = w_vector * I[d in vector] / (rrf_k + rank_vector[d]) + w_keyword * I[d in keyword] / (rrf_k + rank_keyword[d]) # 初始配置：w_vector = 1.0, w_keyword = 1.0 # 只有在离线评测或线上反馈证明某类查询受益时才调整，禁止凭直觉固定 0.7/0.3。
  1. 先建立带人工相关性标签或用户反馈的查询集，至少按“概念问答 / 精确术语 / 数字代码 / 中英混合 / 无结果”分桶；记录 Recall@K、MRR/NDCG@K、答案引用命中率、P95 延迟和关键词故障降级率。
  2. 以等权 RRF 作为 baseline，做离线网格或小流量 A/B：比较 (1,1)、全局偏置权重，以及按 QueryRewriter intent 选择的权重。只有质量显著提升且延迟、误召回可接受时才上线。
  3. 优先使用查询意图加权而非全局固定权重：精确标识符提高 w_keyword，开放式语义问题提高 w_vector；权重必须有上限、可观测并可一键关闭。
  4. 后续引入 Cross-Encoder/BGE-Reranker 时，把 RRF 作为召回融合层，使用 reranker 统一比较候选内容；不要把未经校准的 BM25 和 cosine 原始分数直接相加。
本项目决策：保留等权 RRF 作为 P0 的默认实现，并将“等权只是可验证基线”写入配置与监控要求；新增 RRF_VECTOR_WEIGHT、RRF_KEYWORD_WEIGHT（默认均为 1.0）和按 intent 覆盖的扩展位， 但在没有评测证据前不启用偏置。这样既获得混合检索的低风险收益，也避免把偶然的语料分布固化成错误的全局排名规则。
