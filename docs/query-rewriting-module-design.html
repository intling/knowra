1. 概览与设计目标

当前状态

知寻当前的 RAG 管线将用户原始查询 直接送入向量化+检索流程，缺少查询预处理环节：

用户查询 ──▶ 【本文档聚焦 — 查询重写模块】 │ │ 原始口语化查询，未经任何预处理 │ ▼ (交付给检索模块 → 向量化 → 检索 → LLM 生成) ┊ 虚线部分属于检索与生成模块，不在本文档范围内

核心问题

问题场景示例检索后果
口语化/模糊表达"那个上次说的性能优化方案是啥来着"向量偏离文档中的正式表述
术语不匹配"怎么让电脑跑得更快"知识库中存的可能是"系统性能调优"
多意图纠缠"A 和 B 的区别是什么，怎么选"单一向量无法同时覆盖比较+选型
过度简短"Redis"向量语义空洞，检索结果散乱
多跳推理"导致上次事故的根因是什么"需要先检索"事故"，再检索"根因"
对话上下文缺失"它的配置怎么改"（上文提过 Nginx）丢失指代对象，完全无法检索

设计原则

🎯 Prompt 驱动

所有重写逻辑通过精心设计的 Prompt 实现，不引入额外的模型训练或复杂 NLP 管线。相同的 LLM 基础设施同时用于重写和回答生成。

⚡ 分层渐进

低成本策略优先（直接改写），按需升级至高成本策略（HyDE / Multi-Query）。避免为简单查询浪费计算资源。

🔄 异步非阻塞

原始查询快速返回基础结果；高级重写在后台异步执行，结果到达后进行融合，保证首字节响应时间不受影响。

📊 可观测

每次重写的输入/输出/耗时/策略选择均记录结构化日志，支持后续效果评估与策略迭代。

4. 决策流 — 分层策略路由

意图分类 Prompt

你是一个查询意图分类器。分析用户查询，输出 JSON 格式的分类结果。 ## 分类维度 ### intent (意图类型) - "factual": 查询具体事实、数据、定义（如 "Redis 默认端口是多少"） - "analytical": 需要分析、推理、解释原因（如 "为什么系统在高并发下会崩溃"） - "comparative": 比较两个或多个事物（如 "Postgres 和 MySQL 的区别"） - "procedural": 询问操作步骤、配置方法（如 "如何配置 Nginx 反向代理"） - "exploratory": 开放探索性问题（如 "有哪些方法可以优化数据库性能"） - "chitchat": 闲聊、问候（如 "你好"） - "ambiguous": 意图不明确，过于简短或模糊 ### complexity (1-10) - 1-2: 简单事实查询，单术语，明确的关键词 - 3-5: 中等复杂度，需要一定推理或涉及 1-2 个概念 - 6-8: 复杂查询，多概念、多跳、需要比较或分析 - 9-10: 高度复杂，包含多重意图、需要深度推理和多步检索 ### is_multi_hop (boolean) 是否需要在不同知识点之间进行多步推理才能得到答案 ### has_pronouns (boolean) 查询是否含有指代词（它、那个、这个、其等），需要结合上下文才能理解 ### protected_terms (string[]) 查询中包含的技术术语、专有名词列表，这些词在重写时必须原样保留 ## 用户查询 {query} ## 对话历史（可能为空） {history} ## 输出格式 (严格 JSON) ```json { "intent": "factual", "complexity": 2, "is_multi_hop": false, "has_pronouns": false, "protected_terms": ["Redis"], "reasoning": "简短说明分类理由" } ```

策略路由规则

条件策略说明
complexity ≤ 2 且 intent = "factual" 直接检索 意图明确的简单查询，改写无增益
complexity ≤ 2 且 intent = "chitchat" 直接回复 无需检索知识库
has_pronouns = true 上下文融合 → 重新分类 先消解指代，再判断后续策略
intent = "ambiguous" 或 complexity ≤ 5 规范重述 + 术语对齐 口语→书面、模糊→明确
complexity 6-8 且 intent = "comparative" 多查询生成 (Multi-Query) 从不同角度检索
complexity 6-8 且 is_multi_hop = true 子问题分解 (Decomposition) 拆分子问题逐步检索
complexity ≥ 8 或 intent = "analytical" HyDE + 后退提示词 生成假设文档/抽象问题
complexity ≥ 9 全策略融合 改写 + HyDE + Multi-Query + Decompose 并发
💡 渐进式升级：如果某策略检索结果不理想（结果数 < 阈值 或 最优相似度 > 阈值），自动升级到下一级策略。这是一个"尽力而为、逐级增强"的过程。

5. 重写策略详解

以下每个策略都通过 单一 Prompt 模板 实现。策略之间独立、可组合、可单独开关。

5.1 规范化重述 (Normalize Rewriter)

目标：将口语化、碎片化的查询转为书面化、完整、标准化的表述。

适用：complexity ≤ 5、口语化表达、省略式提问。

成本：⭐ (极低 — 1 次轻量 LLM 调用)

你是一个查询规范化助手。你的任务是将用户的口语化查询重写为书面化、标准化的完整查询语句。 ## 重写规则 1. **补全省略**：将省略的主语、宾语、定语补全，形成完整句子 2. **书面化**：将口语词汇替换为书面表达（如 "咋整" → "如何处理"） 3. **去冗余**：删除无意义的语气词、重复表达、口头禅 4. **保持核心语义**：不添加用户未提及的信息，不改变查询意图 5. **保护专有名词**：以下词汇必须原样保留，不得替换或翻译： {protected_terms} ## 示例 输入: "那个数据库怎么搞快点" 输出: "如何提升数据库的性能" 输入: "上次说的那个bug修复了没" 输出: "之前的软件缺陷是否已修复" 输入: "大模型在医疗这块有啥用" 输出: "大语言模型在医疗领域有哪些应用" ## 对话历史（用于理解上下文，可能为空） {history} ## 用户查询 {query} ## 输出 (仅输出重写后的查询文本，不需要任何解释) 重写查询：

5.2 扩展重述 (Expand Rewriter)

目标：对模糊查询进行语义扩展，补充同义词、上位概念、专业术语及相关维度。

适用：查询过于简短、术语单一、可能遗漏相关知识领域。

成本：⭐⭐ (低)

你是一个查询扩展助手。用户的查询可能过于简短或只覆盖了问题的一个方面，你需要对其进行语义扩展。 ## 扩展规则 1. **同义词补充**：为核心概念添加同义词或近义表达 2. **上位概念**：将具体术语扩展到更广泛的概念层级 3. **相关维度**：补充与查询相关的其他重要维度（如查询"性能"时补充"延迟、吞吐量、资源利用率"） 4. **多角度表述**：从不同角度重新表述同一问题 5. **不改变原意**：扩展应围绕原始查询意图，不引入无关概念 6. **保护专有名词**：以下词汇必须原样保留：{protected_terms} ## 示例 输入: "微服务" 输出: "微服务架构的设计原则、服务拆分策略、服务间通信方式（REST/gRPC/消息队列）、服务治理（注册发现、负载均衡、熔断降级）、分布式事务处理" 输入: "Python性能优化" 输出: "Python程序性能优化方法，包括：代码层面优化（算法选择、数据结构、内置函数）、解释器优化（PyPy/JIT编译）、并发并行（多线程/多进程/异步编程）、内存管理、性能分析工具（cProfile/line_profiler）、C扩展" ## 用户查询 {query} ## 输出 (仅输出扩展后的查询文本，以原始查询开头，用逗号或分号分隔扩展内容) 扩展查询：

5.3 术语对齐 (Term Alignment Rewriter)

目标：将用户的口语化/非正式表达替换为知识库中使用的正式专业术语。

适用：用户使用了非正式表达、行业黑话、缩写、或知识库可能使用不同术语的场景。

成本：⭐⭐ (低，可结合知识库术语表做本地映射)

你是一个术语对齐助手。你需要将用户查询中的口语化、非正式表达替换为正式的专业术语，使其与知识库中的用词一致。 ## 对齐规则 1. **口语 → 术语**：将日常用语替换为领域标准术语（如 "跑程序" → "执行/运行程序"） 2. **缩写展开**：将常见缩写扩展为全称（根据上下文判断是否需要同时保留缩写） 3. **同义词标准化**：将多种表述统一为知识库中最可能使用的标准表述 4. **保留原词**：对于可能存在多种理解的情况，在替换后以括号保留原词 5. **保护专有名词**：以下词汇必须原样保留：{protected_terms} ## 常见术语对齐表 (可配置扩展) | 用户表达 | 正式术语 | |---------|---------| | 电脑 | 计算机 / 个人电脑 | | 跑起来 | 运行 / 执行 / 启动 | | 挂了 / 崩了 | 崩溃 / 故障 / 服务不可用 | | 卡 | 延迟高 / 响应慢 / 阻塞 | | 占内存 | 内存占用 / 内存消耗 | | 加速 | 性能优化 / 加速 | | 存数据 | 数据持久化 / 数据存储 | | 接口 | API / 接口 | | 集群 | 集群 / 分布式集群 | | 热备 | 热备份 / 高可用 | | AI | 人工智能 / AI | | 大模型 | 大语言模型 (LLM) | | 向量库 | 向量数据库 | ## 对话历史 {history} ## 用户查询 {query} ## 输出 (仅输出术语对齐后的查询文本) 对齐查询：
💡 两阶段优化：第一阶段：本地术语表精确匹配替换（零 LLM 成本、零延迟）；第二阶段：对于本地未命中但疑似存在术语不匹配的查询，使用 LLM 进行对齐。本地术语表可以从知识库中定期抽取高频术语自动构建。

5.4 HyDE 策略 (Hypothetical Document Embeddings)

目标：让 LLM 生成一个假设的"理想答案文档片段"，用这个片段的向量去检索，而不是用原始查询向量。

核心原理：假设答案的向量分布更接近真实答案文档的向量分布，比短查询向量更容易匹配到相关内容。

适用：complexity ≥ 6、analytical 意图、抽象概念查询。

成本：⭐⭐⭐ (中高 — 需要 1 次生成 + 1 次向量化)

你是一个技术文档撰写助手。请根据用户的问题，撰写一段假设的知识库文档片段，就像你真的在知识库中找到了相关内容一样。 ## 写作要求 1. **文档风格**：使用正式、客观的技术文档写作风格 2. **内容结构**：包含概念定义、关键要点、技术细节或操作步骤 3. **长度**：200-400 字的中文段落 4. **信息密度**：尽可能包含与问题相关的关键术语、概念和事实 5. **不要编造**：不要凭空编造不存在的数据或事实；如果有不确定的地方，使用通用的、教科书级别的描述 6. **不要回答用户问题**：你写的是一段"文档"，不是对用户问题的直接回答 ## 保护术语（必须原样保留） {protected_terms} ## 用户问题 {query} ## 输出 (仅输出假设文档内容，无需标记或说明)

HyDE 分层启用条件

条件是否启用 HyDE理由
简单事实查询 (complexity ≤ 2)❌ 跳过直接检索即可满足
包含具体实体名称/编号❌ 跳过精确匹配更有效
分析/推理性查询✅ 启用HyDE 擅长补全推理链条
抽象概念查询（如"怎么设计高可用系统"）✅ 启用短查询向量语义稀疏
情感/观点类查询✅ 启用主观内容更难用关键词匹配
普通改写后检索结果不足✅ 回溯启用作为 fallback 策略

5.5 多查询生成 (Multi-Query Rewriter)

目标：从不同角度生成 3-5 个查询变体，分别检索后融合结果，覆盖原始查询的不同侧面。

适用：complexity 6-8、comparative 意图、多概念查询。

成本：⭐⭐⭐ (中高 — 1 次 LLM 生成 + N 次向量检索)

你是一个查询扩展助手。针对用户的复杂问题，从不同角度生成多个查询变体，每个变体侧重问题的不同侧面。 ## 生成规则 1. 生成 3-5 个查询变体 2. 每个变体应是独立的、可直接用于检索的完整查询 3. 变体之间应覆盖不同的角度、维度或侧重点 4. 有些变体可以更具体（聚焦细节），有些可以更宽泛（覆盖背景） 5. 所有变体必须围绕原始问题的核心意图 6. **保护专有名词**：以下词汇在所有变体中必须原样保留：{protected_terms} ## 示例 原始查询: "微服务架构的优缺点" 变体: 1. "分布式系统中的数据一致性和可用性权衡" ## 用户查询 {query} ## 输出格式 (每行一个变体，以 "- " 开头，纯文本即可) - 变体1 - 变体2 - ...

5.6 子问题分解 (Decomposition Rewriter)

目标：将复杂的多跳问题拆分为 2-4 个简单的子问题，每个子问题可独立检索，然后按依赖顺序或并行执行。

适用：is_multi_hop = true、需要多步推理的问题。

成本：⭐⭐⭐⭐ (高 — N 次 LLM 调用 + N × M 次检索)

你是一个问题分解助手。将用户的复杂问题拆分为 2-4 个简单子问题，每个子问题可以独立检索和回答，最终合并得到完整答案。 ## 拆分规则 1. **原子性**：每个子问题应足够简单，可以通过一次检索 + 一次回答解决 2. **完整性**：所有子问题合起来应能完整覆盖原始问题的全部意图 3. **依赖标注**：如果子问题之间存在先后依赖关系，请标注顺序 4. **独立性**：无依赖的子问题应可并行处理 5. **保护专有名词**：以下词汇在所有子问题中必须原样保留：{protected_terms} ## 示例 原始查询: "导致上次生产环境事故的根因是什么，我们应该怎么预防类似问题" 子问题: 1. [优先级1, 无依赖] "生产环境最近发生的事故详情和影响范围" 2. [优先级2, 依赖:1] "分析该事故的根本原因和技术层面触发条件" 3. [优先级3, 依赖:2] "针对该根因的预防措施和监控改进方案" 4. [优先级3, 依赖:2] "类似场景的自动化检测和告警机制设计" 原始查询: "对比 React 和 Vue 的响应式原理，并说明在大型项目中应该如何选择" 子问题: 1. [无依赖] "React 的响应式更新原理（虚拟DOM、Fiber 协调、状态管理）" 2. [无依赖] "Vue 的响应式原理（Proxy 响应式系统、依赖追踪、组件更新）" 3. [依赖:1,2] "React 和 Vue 在大型项目中的选型考量因素（性能、生态、团队、可维护性）" ## 用户查询 {query} ## 输出格式 - [优先级N, 依赖:N或"无依赖"] "子问题描述"

5.7 后退提示词 (Step-Back Rewriter)

目标：从具体问题中"后退"一步，抽象出更高层级的基础原理或通用规则，先检索这些基础概念，再结合具体问题进行推理。

适用：complexity ≥ 7、需要先理解基础概念才能回答的具体问题。

成本：⭐⭐⭐ (中)

你是一个问题抽象助手。用户的查询是一个具体问题，请"后退"一步，识别这个问题背后涉及的基础原理、通用规则或核心概念，生成一个更抽象、更通用的查询。 ## 后退规则 1. **识别问题背后的基础原理**：用户问具体问题 → 你识别出背后的通用概念 2. **抽象层级上移**：从"怎么做X"退到"X的基本原理是什么" 3. **保持相关性**：抽象后的问题必须与原始问题相关，不是无目的的泛化 4. **生成检索用查询**：抽象后的问题应该是适合在技术文档中检索的标准化表述 ## 示例 原始查询: "为什么我的 Spring Boot 应用在 K8s 上 OOM 了" 后退查询: "Java 应用在 Kubernetes 容器环境中的内存管理机制和 OOM 原因分析" 原始查询: "这段 Python 代码用了 asyncio 但还是慢，怎么优化" 后退查询: "Python asyncio 异步编程的性能瓶颈分析方法和优化策略" 原始查询: "GPT-4 和 Claude 在代码生成上哪个更强" 后退查询: "大语言模型代码生成能力的评估维度和基准测试方法" ## 用户查询 {query} ## 保护术语（必须原样保留） {protected_terms} ## 输出 (仅输出后退后的抽象查询) 后退查询：

5.8 上下文依赖处理 (Context Rewriter)

目标：在多轮对话中，将用户含有指代词或省略主题的查询改写为独立、完整的查询。

适用：has_pronouns = true、多轮对话场景。

成本：⭐ (极低)

你是一个对话理解助手。用户的当前查询可能含有指代词（它、那个、这个、其等）或省略了上文提到的主题。请结合对话历史，将当前查询改写为一个独立、完整、不依赖任何上下文的查询。 ## 改写规则 1. **指代消解**：将所有指代词替换为对话历史中对应的具体实体 2. **主题补全**：如果用户省略了当前讨论的主题，从历史中补全 3. **保持意图**：不要改变用户的原始意图和问题方向 4. **不要添加历史中不存在的信息** 5. **如果当前查询已经是独立完整的，原样返回** ## 对话历史 {history} ## 当前用户查询 {query} ## 输出 (仅输出改写后的独立查询) 独立查询：

上下文压缩策略（长对话优化）

你是一个对话摘要助手。以下是一段较长的多轮对话历史。请将对话压缩为简洁的上下文摘要， 保留与当前查询可能相关的关键信息（讨论的主题、提到的实体、达成的共识、未解决的问题）。 ## 压缩规则 1. 保留所有专有名词、技术术语、产品名称 2. 保留用户明确关注的问题领域 3. 省略寒暄、过渡性对话 4. 摘要不超过 300 字 ## 对话历史 {history} ## 输出 (简洁的上下文摘要)

5.10 意图分类与路由 (新增策略)

目标：在重写之前先对查询进行意图分类，根据类别选择最适合的重写路径，避免"一刀切"。

创新点：将分类和路由作为独立的前置步骤，实现"查询分流"。

不同类型的查询对检索的需求完全不同：事实型查询需要精确匹配，分析型查询需要覆盖推理链，操作型查询需要找到步骤说明。使用相同的重写策略处理所有查询，就像用同一把钥匙开所有锁。

5.11 自省式迭代重写 (Self-Reflective Rewriting) (新增策略 · 跨模块协作)

目标：重写模块支持接收来自检索模块的"回溯"信号——当检索结果不充分时，升级策略重新改写。这是重写模块与检索模块之间的协作接口。

适用：所有策略的最后防线，作为质量保障的"安全网"。

成本：⭐⭐ (仅在检索模块触发回溯时产生额外改写成本)

重写模块负责：收到回溯信号后，根据建议升级策略（如从规范重述升级为 HyDE），生成新的改写结果返回给检索模块。

5.12 对比式重写 (Contrastive Rewriter) (新增策略)

目标：对于比较类查询，从"共同点"和"差异点"两个方向生成检索查询，确保检索完整覆盖对比的两个维度。

5.15 改写质量评估与回溯 (新增策略)

目标：对改写结果进行质量评分，低于阈值的改写自动丢弃或触发回溯。确保改写不会"越改越差"。

你是一个查询改写质量评估器。请对比原始查询和改写后的查询，评估改写质量。 ## 评估维度 (每个 1-5 分) 1. **语义保留度**：改写是否完整保留了原始查询的核心意图和语义？ 2. **清晰度提升**：改写后的查询是否比原始查询更清晰、更具体、更容易检索？ 3. **信息增量**：改写添加的扩展信息是否相关且有用？（注意：过度扩展是减分项） 4. **术语准确性**：专业术语使用是否准确？是否有不当替换？ 5. **可检索性**：改写后的查询是否更适合在向量数据库中进行语义检索？ ## 原始查询 {original_query} ## 改写查询 {rewritten_query} ## 改写策略 {strategy_name} ## 输出 JSON ```json { "semantic_preservation": 5, "clarity_improvement": 4, "information_gain": 3, "term_accuracy": 5, "retrievability": 4, "total_score": 21, "verdict": "good", "issues": [] } ``` ## 判断规则 - total_score ≥ 20 → verdict: "excellent" - total_score 15-19 → verdict: "good" - total_score 10-14 → verdict: "marginal" (建议回溯) - total_score < 10 → verdict: "poor" (丢弃改写，回退原始查询) - semantic_preservation < 3 → 自动 verdict: "poor"（语义偏离是不可接受的）

结果融合算法：RRF (Reciprocal Rank Fusion)

📌 属于检索模块：RRF (Reciprocal Rank Fusion) 用于将多个改写查询的检索结果进行融合排序，属于检索与生成模块的职责范围。重写模块的输出为改写后的查询列表，交由检索模块进行并发检索和 RRF 融合。RRF 的详细设计将在检索模块设计文档中给出。
def reciprocal_rank_fusion( result_sets: list[list[SearchResult]], # 每个查询的检索结果 k: int = 60, # RRF 平滑常数 top_k: int = 5, # 最终返回数量 ) -> list[SearchResult]: """将多个查询的检索结果进行 RRF 融合。 每个文档的最终得分 = Σ 1/(k + rank_i) 其中 rank_i 是该文档在第 i 个结果集中的排名。 k=60 是经过大量实验验证的最优默认值（参考 TREC 评估）。 注意：此算法属于检索模块，此处仅作为接口约定展示。 """ scores: dict[str, float] = {} doc_map: dict[str, SearchResult] = {} for result_set in result_sets: for rank, doc in enumerate(result_set, start=1): key = str(doc.chunk_id) scores[key] = scores.get(key, 0.0) + 1.0 / (k + rank) if key not in doc_map: doc_map[key] = doc # 按融合分数降序排列 sorted_ids = sorted(scores, key=scores.get, reverse=True) return [doc_map[id] for id in sorted_ids[:top_k]]

7. 缓存与去重机制

三级缓存架构

层级缓存类型命中条件存储TTL
L1 精确匹配缓存 query_hash 完全一致 内存 LRU (128MB) 1 小时
L2 语义相似缓存 query 向量余弦距离 ≤ 0.05 内存 LRU (256MB) 6 小时
L3 热点统计缓存 被访问 ≥ 5 次/小时 Redis / 内存 24 小时

微批请求去重

时间窗口 T (默认 100ms) 内到达的请求: Req A: "如何优化数据库性能" Req B: "如何优化数据库性能" ← 与 A 完全相同 → 合并, 等待 A 的结果 Req C: "数据库怎么加速" ← 与 A 语义相似 (cosine < 0.05) → 合并 Req D: "Python 性能优化" ← 与 A 无关 → 独立处理 合并结果: A、B、C 共享同一份检索结果，避免重复计算。

缓存 Key 设计

# L1 缓存 key: 查询文本哈希 l1_key = f"qrew:l1:{hashlib.sha256(query.encode()).hexdigest()[:16]}" # L2 缓存 key: 查询向量聚类 ID (向量量化后的桶 ID) # 使用 pgvector 或本地向量量化 l2_key = f"qrew:l2:{quantize(query_vector, n_buckets=1024)}" # L3 缓存 key: 带时间窗口的热点 key l3_key = f"qrew:l3:{date}:{l1_key}"
