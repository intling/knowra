knowra 向量存储方案（pgvector Native Storage）

本文定义将当前 JSON 浮点数组形式的文档向量迁移到 pgvector 原生 vector(N) 类型列的完整方案。 在已完成向量化（Cloud Embedding）的基础上，引入 pgvector 原生向量列和双写策略， 为后续向量索引和语义检索做好基础设施准备。本阶段不实现向量索引和语义搜索。

阶段：方案设计 日期：2026-07-17 推荐变更：add-vector-storage 向量维度：2560 存储类型：pgvector vector(2560) 前置能力：document-embedding 已实现 后续规划：向量索引 & 语义检索 & 混合检索（独立变更）

1. 背景与产品意图

1.1 当前状态

knowra 已完成文档向量化能力（document-embedding），chunk 文本通过 Qwen/Qwen3-Embedding-4B 云端 API 转化为 2560 维稠密向量， 并以 JSON 浮点数组形式存储在 document_embeddings.embedding_json 列中。

1.3 产品意图

  • 将 JSON 向量数据迁移至 pgvector 原生 vector(2560) 类型，解锁数据库层级的向量操作。
  • 采用双写策略（JSON + vector 列并存），保留 JSON 列作为人类可读参考和故障恢复备份。
  • 对既有数据执行安全回填，确保新老数据统一纳入 pgvector 列。
  • 不改变现有的 embedding API 接口和前端行为，变更完全限定在后端数据层。
  • 为后续向量索引（HNSW/IVFFlat）和语义检索提供标准化的 pgvector 原生向量列。

2.1 候选方案对比

2.2 决策：pgvector

选择 pgvector 的理由

🏗️ 零新增基础设施

PostgreSQL 18 容器已运行，pgvector 扩展已启用（CREATE EXTENSION vector）， Python 包 pgvector>=0.4.0 已在依赖中。引入方案只需一个 Alembic 迁移即可上线。

⚡ 规模完全匹配

knowra 是个人知识库工具，文档量级在千到万级，chunk 在万到十万级。 pgvector 的 HNSW 索引在此规模下可达到亚毫秒级 ANN 查询，远超需求。

🔄 事务内联查询

向量搜索可与用户权限过滤（WHERE owner_user_id = $1）、文档元数据 JOIN、 时间排序等在一条 SQL 中完成。不需要跨服务协调两套查询结果。

🔧 运维简单

个人项目不需要维护额外的 Milvus/Qdrant 容器。备份 PostgreSQL 就等于备份了向量数据。 Docker Compose 只需管理一个数据库服务。

当未来数据量增长到亿级向量时，可考虑引入专门的向量数据库作为扩展层。 但 pgvector 作为起点已经足够覆盖从零到百万级的完整增长曲线。

3. 向量索引规划（后续阶段）

本阶段不实现向量索引

向量索引（HNSW / IVFFlat）将在后续独立变更中实现。本节仅记录初步调研结论，供后续索引方案设计参考。

3.1 HNSW vs IVFFlat 对比

对比维度 HNSW IVFFlat
原理 分层可导航小世界图 — 构建多层图结构，搜索时从顶层粗粒度向底层细粒度导航 倒排文件 + k-means 聚类 — 将向量空间划分为 N 个聚类，搜索时只扫描最近的几个聚类
查询速度 快 — O(log N) 图遍历，适合实时查询 中等 — 依赖于探测的聚类数量（probes）
是否需要训练 否 — 不需要显式训练步骤 是 — 需要先有足够数据后执行 lists 参数调优
插入后索引状态 立即可用 — 新向量插入时就加入图结构 新向量落入已有聚类，但长期插入后聚类质量下降，需重建
适用场景 持续增量的动态数据集、实时查询 相对静态的数据集、批量导入场景
初步倾向：HNSW

knowra 作为知识库工具，文档持续上传、chunk 持续生成，是一个动态增长的数据集。 HNSW 不需要训练步骤、支持即时插入、查询速度快，是更适合的索引类型。 具体参数（m、ef_construction、距离度量）将在索引实现阶段确定。

3.2 本阶段与索引的关系

本阶段的 embedding_vector vector(2560) 列是实现向量索引的必要前提：

  • pgvector 索引（HNSW / IVFFlat）必须在 vector(N) 类型列上创建，JSON 列无法被索引。
  • 双写策略确保索引创建时所有向量已就位，无需再次回填。
  • 索引创建将是纯 DDL 操作（CREATE INDEX ... USING hnsw），不涉及数据迁移。

5. 数据回填方案

5.1 回填策略

现有 document_embeddings 表中的 embedding_json 列已包含完整的 2560 维浮点数组。 回填策略是从 JSON 列转化写入到新的 embedding_vector 列，无需重新调用 embedding API。

① Schema 迁移 添加 embedding_vector vector(2560) 列（nullable）。
② 数据回填 UPDATE ... SET embedding_vector = embedding_json::vector
③ 验证回填 抽查行确认 embedding_vector 值与 embedding_json 一致。
④ 添加约束 验证通过后可选添加 NOT NULL 约束。

5.2 回填安全性考量

风险缓解措施
回填期间表锁导致写入阻塞 使用批量 UPDATE ... WHERE id IN (SELECT id ... LIMIT N) 分批回填， 每批 500~1000 行，批次之间 commit 释放锁。
pgvector 的 ::vector 转换是纯 CPU 操作，不涉及 IO， 每批执行时间应在秒级。
JSON 中存在非数值或维度错误的数据 回填前执行验证查询：
SELECT id FROM document_embeddings WHERE jsonb_array_length(embedding_json) != 2560
对异常行跳过并记录日志。
回填后新旧列数据不一致 回填完成后抽样验证：
SELECT COUNT(*) FROM document_embeddings WHERE embedding_vector IS DISTINCT FROM embedding_json::vector
应为 0。
长时间运行的回填被中断 每批提交事务（而非一个大事务），中断后可从中断点附近继续。 支持幂等重跑：WHERE embedding_vector IS NULL。

6. 代码改动清单

6.1 模型层 (models)

文件改动说明
models/document_embedding.py 在 DocumentEmbedding 中新增 embedding_vector 字段 使用 pgvector.sqlalchemy.Vector 类型：
embedding_vector: object = Field(sa_column=Column(Vector(2560), ...))
与现有 sa_column=Column(JSON) 模式一致。
SQLModel + pgvector 使用要点
由于 SQLModel 无法直接类型化 pgvector 的 Vector 类型（与 JSON 列类似）， 我们使用 sa_column=Column(Vector(2560)) 绕过 SQLModel 的类型系统， 与现有 embedding_json 列的声明方式完全一致。运行时 pgvector 库会自动处理 Python list ↔ pgvector 的序列化。

6.2 服务层 (services)

文件改动说明
services/document_embedding.py 更新 _save_embeddings() 在创建 DocumentEmbedding 时增加 embedding_vector=result.embedding。 pgvector 库会自动将 list[float] 转化为 vector(2560)。

9. 风险与缓解

风险影响概率缓解措施
回填期间阻塞线上写入 中 低 分批提交、每批 500 行；回填 WHERE embedding_vector IS NULL 支持幂等续跑； 如有关键写入可暂停回填、稍后继续。
pgvector Python 版本与 DB 扩展版本不匹配 中 低 使用 pgvector/pgvector:pg18 最新镜像 + pgvector>=0.4.0。 在 CI 中验证 CREATE EXTENSION vector + 建表 + 插入 + 查询。
双写增加磁盘空间 低 高 每个 2560 维向量约 20KB（JSON）+ 10KB（vector 二进制）， 1 万个 embedding 约 300MB。对于知识库体量完全可接受。
