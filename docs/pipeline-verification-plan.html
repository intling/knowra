关键缺失：我们写入了向量，但从未验证能否把向量取出来并还原为原始分块内容。

1.2 核心问题

🔍 数据完整性未知

document_embeddings 表中存有向量，document_chunks 表中存有分块文本， 但没有人验证过二者之间的关联是否完整、一致、可还原。

🔗 关联链路未验证

embedding → chunk (via chunk_id) → text → document 的完整还原链路 从未被端到端验证过。如果某个环节断裂（如孤儿向量、缺失文本），当前系统无法发现。

📊 无可视化确认

开发者无法直观看到「存进去的 2560 维向量」对应的是「哪段中文/英文文本」。 这为后续检索和 RAG 阶段的调试埋下隐患。

🛡️ 无回归防护

未来修改分块策略、换用嵌入模型、或调整 pipeline 时，没有自动化验证来确保 「向量 ↔ 分块内容」的映射关系没有被破坏。

1.3 本阶段目标

🎯 目标：实现一条只读验证链路—— 从 pgvector 中取出已存储的向量，通过 JOIN 还原为原始分块文本， 并以结构化方式展示全链路数据，确认存取一致。
明确 NOT 本阶段：用户输入查询、语义搜索、RAG 问答、向量索引优化。

3.2 设计原则

🔒 只读验证

验证端点不修改任何数据库记录，不触发任何写入操作。纯 SELECT + 文件读取。 安全、幂等、可随时调用。

🔄 复用现有基础设施

复用 ChunkArtifactStorage 读取大文本文件； 复用 get_current_user() 做权限校验； 复用 get_latest_active_embedding_job() 查找活跃作业。

📐 标准项目模式

遵循项目既有的 Service → Route → Schema 分层架构； 使用 SQLModel session 管理； 使用 structlog 结构化日志。

5. 数据完整性检查矩阵

以下 7 项检查覆盖了「向量 ↔ 分块」映射关系中所有可能的数据异常。

# 检查项 检查逻辑 失败意味着 严重度
1 chunk_embedding_pairing
分块-向量对应关系		 对每个 embedding JOIN chunk，确认所有 chunk 都有 embedding，所有 embedding 都能找到 chunk。 检测孤儿 embedding（有 embedding 但 chunk 被删除）和孤儿 chunk（有 chunk 但没有 embedding）。 • 孤儿 embedding：向量化后 chunk 被意外删除
• 孤儿 chunk：向量化作业不完整，部分 chunk 未成功向量化 		🔴 严重
2 dimension_consistency
向量维度一致性		 验证每条 embedding 的 dimensions 字段与 job 声明的维度一致， 且 embedding_vector 实际长度与声明维度匹配。 可能同一文档中混用了不同维度的嵌入模型，后续检索时余弦相似度计算会出错。 🔴 严重
3 sequence_continuity
序号连续性		 验证 sequence_index 从 0 开始连续递增至 N-1（N=chunk_count）， 无重复、无跳号。 序列断裂意味着分块过程中可能丢失或重复了某些块， 后续按顺序溯源时会出现错位。 🟡 警告
4 chunk_text_availability
分块文本可读性		 遍历所有 chunk，如果 text 非空则直接使用； 如果为 NULL 则通过 text_storage_key 从文件系统读取。 确认所有 chunk 的文本最终都能成功获取。 文件系统存储的 chunk 文本文件被删除、移动或损坏。 🔴 严重
5 contextualized_text_availability
上下文增强文本可读性		 同检查 4，但针对 contextualized_text 字段。 验证所有 chunk 的上下文增强文本均可成功获取。 contextualized_text 文件丢失但普通 text 可能仍在， 影响后续 RAG 检索质量但不影响基础功能。 🟡 警告
6 token_count_consistency
Token 数有效性		 验证所有 chunk 和 embedding 的 token_count 非 NULL 且 > 0。 检查 chunk.token_count 和 embedding.token_count 的一致性 （允许少量差异，因为分块 tokenizer ≠ embedding tokenizer）。 token_count 为 NULL 或 0 意味着分词过程异常， 但不影响向量质量和检索能力。 ℹ️ 信息
7 model_consistency
嵌入模型一致性		 验证所有 embedding 记录使用相同的 model 字段值。 同一文档的所有向量应来自同一个嵌入模型。 混用模型可能导致向量空间不一致，跨 chunk 的相似度比较失去意义。 🔴 严重
检查结果语义：单条检查passed: false 并不使 HTTP 响应变为 4xx/5xx。 验证端点始终返回 200，将检查结果内嵌在 verification.checks[] 中。 这允许前端同时展示所有检查项的状态（通过/失败/警告）， 而非在第一个失败处就中断。

6. 服务层设计

6.1 PipelineVerificationService

# backend/app/services/pipeline_verification.py

from dataclasses import dataclass
from uuid import UUID
from sqlmodel import Session

@dataclass
class PipelineVerificationResult:
    """存取验证的完整结果。"""
    document: DocumentChainInfo
    pipeline: PipelineStageInfo
    verification: VerificationSummary
    pairs: list[ChunkEmbeddingPair]
    stats: VerificationStats

class PipelineVerificationService:
    """流水线存取验证服务。

    职责：给定 parsed_document_id，沿 JOIN 链路取出所有分块-向量 pairs，
    解析文件系统中的溢出文本，执行完整性检查，返回结构化验证结果。
    """

    def __init__(
        self,
        *,
        session: Session,
        chunk_storage: ChunkArtifactStorage,
        config: EmbeddingConfig,
    ) -> None: ...

    def verify(self, parsed_document_id: UUID) -> PipelineVerificationResult:
        """执行完整的存取验证流程。"""
        # 1. 加载文档链路信息
        doc_chain = self._load_document_chain(parsed_document_id)
        # 2. 确认 pipeline 每阶段均成功
        self._validate_pipeline_complete(doc_chain)
        # 3. JOIN chunks ↔ embeddings
        pairs = self._load_chunk_embedding_pairs(doc_chain)
        # 4. 解析文件系统文本
        self._resolve_chunk_texts(pairs)
        # 5. 执行完整性检查
        checks = self._run_integrity_checks(pairs, doc_chain)
        # 6. 组装结果
        return self._build_result(doc_chain, pairs, checks)

6.2 核心查询：chunks ↔ embeddings JOIN

def _load_chunk_embedding_pairs(self, doc_chain) -> list[ChunkEmbeddingPair]:
    """通过 chunk_id JOIN 两张表，按 sequence_index 排序。

    使用 SQLModel/SQLAlchemy 的 ORM 关系加载，
    避免 N+1 查询 —— 使用 joinedload 或子查询预加载。
    """

    # 单次查询获取所有分块
    chunks = self.session.exec(
        select(DocumentChunk)
        .where(DocumentChunk.chunk_job_id == doc_chain.chunk_job.id)
        .order_by(DocumentChunk.sequence_index)
    ).all()

    # 单次查询获取所有向量
    embeddings = self.session.exec(
        select(DocumentEmbedding)
        .where(DocumentEmbedding.embedding_job_id == doc_chain.embedding_job.id)
        .order_by(DocumentEmbedding.sequence_index)
    ).all()

    # 以 chunk_id 为 key 构建映射
    embedding_by_chunk = {e.chunk_id: e for e in embeddings}

    # 组装 pairs
    pairs = []
    for chunk in chunks:
        emb = embedding_by_chunk.get(chunk.id)
        pairs.append(ChunkEmbeddingPair(
            sequence_index=chunk.sequence_index,
            chunk=chunk,
            embedding=emb,          # None 时触发"孤儿 chunk"检查
        ))

    # 反向检查：有无 orphan embedding
    chunk_ids = {c.id for c in chunks}
    for emb in embeddings:
        if emb.chunk_id not in chunk_ids:
            pairs.append(ChunkEmbeddingPair(
                sequence_index=emb.sequence_index,
                chunk=None,         # ← orphan embedding
                embedding=emb,
            ))

    return sorted(pairs, key=lambda p: p.sequence_index)

6.3 文件系统文本解析

复用现有组件：直接使用 ChunkArtifactStorage.path_for() 方法 将 text_storage_key 和 contextualized_text_storage_key 转换为文件系统路径，然后读取文件内容。 
def _resolve_chunk_texts(self, pairs: list[ChunkEmbeddingPair]) -> None:
    """解析文件系统中的大文本。

    对于每个 pair：
    - 如果 chunk.text 非空 → text_source = "inline"
    - 如果 chunk.text 为 NULL 且有 text_storage_key → 从文件系统读取
    - 对 contextualized_text 做同样处理
    """
    for pair in pairs:
        if pair.chunk is None:
            continue

        # 解析普通文本
        if pair.chunk.text is not None:
            pair.resolved_text = pair.chunk.text
            pair.text_source = "inline"
        elif pair.chunk.text_storage_key is not None:
            path = self.chunk_storage.path_for(pair.chunk.text_storage_key)
            pair.resolved_text = path.read_text(encoding="utf-8")
            pair.text_source = "file"

        # 解析上下文增强文本
        if pair.chunk.contextualized_text is not None:
            pair.resolved_contextualized_text = pair.chunk.contextualized_text
            pair.contextualized_text_source = "inline"
        elif pair.chunk.contextualized_text_storage_key is not None:
            path = self.chunk_storage.path_for(
                pair.chunk.contextualized_text_storage_key
            )
            pair.resolved_contextualized_text = path.read_text(encoding="utf-8")
            pair.contextualized_text_source = "file"

7.3 交互流程

  1. 页面加载 → 调用 GET /api/uploads/.../parsed-document 获取当前用户的所有已解析文档列表，填充下拉选择器
  2. 用户选择文档 → 点击「执行验证」
  3. 加载状态 → 显示骨架屏 + "正在查询数据库并解析文件系统文本…"
  4. 结果展示 → 渲染文档信息、Pipeline 链路、验证摘要、分块-向量对照表
  5. 空状态 → 若选中文档无完成的分块/向量化，显示具体哪个阶段缺失
  6. 错误状态 → 若 API 返回 4xx/5xx，显示错误详情并建议下一步操作

12. 风险与注意事项

⚠️ 大文档性能
数百个 chunk 的文档会导致 pairs 数组较大（每个 pair 包含文本 + 向量预览）。 建议对向量预览只返回前 5 维而非全部 2560 维。完整向量值可通过点击单条展开查看。
⚠️ 文件系统依赖
验证服务依赖 ChunkArtifactStorage 读取文件系统。 如果 storage/chunks/ 目录被手动清理或迁移后路径变化， 文本解析会失败。应确保 STORAGE_DIR 配置正确。
💡 纯只读操作
本服务不修改任何数据。当发现完整性检查失败时， 服务不会自动修复 —— 它只报告问题。修复应通过重新触发 pipeline 流程完成。
💡 可扩展性
如果未来需要验证多个文档，可以在前端循环调用验证 API。 不建议在后端实现批量验证（N+1 查询问题），除非明确需要。
