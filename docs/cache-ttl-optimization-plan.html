一、现状分析：三个核心问题的回答

1.1 什么情况下会缓存？

L1 精确缓存（会话绑定）

触发条件：每次 QueryRewriter 或 SearchService 成功执行后自动写入，Key = session_id + query_hash。

组件缓存内容写入位置
QueryRewriter RewriteResult query_rewriter.py:768
SearchService SearchResponse search.py:359

特别注意：QueryRewriter 的失败/超时降级场景不会写入 L1 缓存，但 SearchService 所有三种场景都会写（正常、无匹配、零向量）。

L2 语义缓存（跨会话）

触发条件：仅 QueryRewriter 管线成功执行后写入，含知识分类标记。

写入位置：query_rewriter.py:773

分类逻辑：

  • general_knowledge → 可跨会话复用
  • context_dependent → 仅同会话可用

SearchService 没有 L2 缓存。

1.2 缓存过期如何处理？

当前策略：纯惰性淘汰（Lazy Eviction）

  • 检查时机：仅在 lookup() / lookup_l2() 被调用时检查 TTL（cache_manager.py:84）
  • 过期行为：时间戳差值 > TTL → 删除条目 → 返回 None
  • 没有的特性：
    • ❌ 无后台定时扫描清理过期条目
    • ❌ 无主动通知/回调机制
    • ❌ 无持久化（进程重启全部丢失）
    • ❌ 无条目级差异化 TTL（所有条目共用同一过期时间）
  • 实际影响：如果某个会话的查询只执行了一次且不再访问，其缓存条目将在内存中完整存活到 TTL 结束 + 直到 LRU 淘汰。

1.3 是否正常、无匹配、零向量都会存储？

是的 —— SearchService 三种场景均存入 L1 缓存

场景缓存行为代码位置
正常结果 有匹配 + LLM 回答 ✅ 存入 L1 search.py:359-371
无匹配 rows=0（向量搜索无结果或被阈值过滤） ✅ 存入 L1 search.py:316-319
零向量 total_searched=0（知识库无任何向量化文档） ✅ 存入 L1 search.py:272-275

问题严重性：无匹配和零向量响应价值极低（只是固定短语），但它们与正常 LLM 生成的响应使用完全相同的 TTL 和缓存空间。这不仅浪费内存，还会导致 LRU 淘汰时挤掉真正有价值的正常结果缓存。

二、问题诊断：缓存时间过长的根因

当前 TTL 配置一览

缓存层默认 TTL说明
QueryRewriter L13600 秒（1 小时）CacheManager 构造默认值，见 cache_manager.py:53
QueryRewriter L23600 秒（1 小时）与 L1 共用同一个 ttl_seconds 参数
SearchService L1600 秒（10 分钟）可配置：SEARCH_CACHE_TTL_SECONDS，见 config.py:114

根本原因分析

  1. 一刀切的 TTL：所有类型的结果（正常/无匹配/零向量）使用相同 TTL，语义上不合理的"负面结果"缓存了过长时间。
  2. 惰性淘汰依赖访问：不被访问的过期条目不会主动释放，持续占用内存。在低流量或长尾查询场景下，过期条目比例可能很高。
  3. 无 TTL 分段策略：没有根据查询类型（通用知识 vs 上下文依赖）、用户行为模式等动态调整 TTL。
  4. L1 改写缓存 1 小时过长：对于实时对话场景，1 小时前的改写结果可能已不适用（知识库更新、上下文变化）。
  5. 缺乏缓存驱逐监控：没有 hit rate、eviction rate、expired ratio 等指标，无法判断 TTL 设置是否合理。

三、决策记录

以下决策经过分析与确认，作为后续实施的依据：

D1：条目级 TTL（方式 A）

在 store() 中增加 ttl_override 参数，每条缓存记录独立存储自己的 TTL。统一 LRU 池保证低价值条目被自然淘汰，DI 链零改动，与 Redis 迁移路径一致。Python/AI 缓存生态（cachetools、LangChain、LlamaIndex、GPTCache）均采用 per-entry TTL。

D2：TTL 值确认

缓存场景TTL理由
QueryRewriter L1 - 通用知识1800s (30min)改写结果稳定性中等；30 分钟在新鲜度与命中率间取平衡
QueryRewriter L1 - 上下文依赖300s (5min)对话上下文快速变化
QueryRewriter L23600s (1h)跨会话通用知识价值高，可保持较长
SearchService L1 - 正常结果600s (10min)包含 LLM 生成文本，10 分钟合理
SearchService L1 - 无匹配不缓存仅固定短语，缓存价值极低，直接跳过即可
SearchService L1 - 零向量不缓存通常是知识库未初始化，缓存无意义

D3：写入时抽样清理

每 N 次写入触发一次随机抽样清理，检查 20 条随机条目是否过期并移除。参考 Redis active-expiration 设计，轻量、零额外 CPU 开销。

D4：结构化日志输出统计，不暴露 HTTP 端点

项目无用户认证系统，暴露 /admin 端点有安全风险。进程重启后内存统计归零，端点数据不可靠。统计数据通过结构化日志输出（每 5 分钟快照），可接入 ELK/Loki 等日志管道做可视化。与 LangChain、LlamaIndex、GPTCache 惯例一致。

D5：暂不引入 Redis

当前单实例内存缓存在功能上足够，且 per-entry TTL + 写入时抽样的方案在向 Redis 迁移时语义直接映射，无架构阻抗。后期实现多 work 队列时再评估。

四、方案一：条目级差异化 TTL（P0）

4.1 设计思路

参考 LangChain / LlamaIndex / GPTCache / cachetools 缓存最佳实践，通过在 store() 中增加 ttl_override 参数，实现每条缓存记录独立存储 TTL。不同类型的结果设置不同的过期时间，在统一 LRU 池中竞争。

  • 高质量 LLM 生成回答 → 较长 TTL：LLM 调用成本高、延迟大，值得长时间缓存
  • 无匹配/零向量 → 不缓存：固定文本无 LLM 成本，低价值，缓存无意义
  • 通用知识改写 → 较长 TTL：跨会话复用价值高
  • 上下文依赖改写 → 短 TTL：依赖对话历史，快速失效

数据结构变更：存储元组从 (timestamp, value) 升级为 (timestamp, ttl, value)。

4.2 实现细节

CacheManager 内部变更

# cache_manager.py

class CacheManager:
    def store(
        self, session_id: str, query_hash: str, result: Any,
        *, ttl_override: float | None = None  # ← 新增：None 时回退到实例默认 TTL
    ) -> None:
        composite_key = self._make_composite_key(session_id, query_hash)

        if composite_key in self._store:
            self._store.move_to_end(composite_key)

        effective_ttl = ttl_override if ttl_override is not None else self._ttl
        self._store[composite_key] = (time.monotonic(), effective_ttl, result)  # ← 三元组

        while len(self._store) > self._max_size:
            evicted_key, _ = self._store.popitem(last=False)
            self._stats["evictions"] += 1
            self._logger.debug("cache_evicted", composite_key=evicted_key)

        self._write_count += 1
        self._maybe_sweep()        # ← 方案二的写入时抽样
        self._maybe_log_stats()    # ← 方案四的统计快照
        self._logger.debug("cache_stored", session_id=session_id, query_hash=query_hash)

    def lookup(self, session_id: str, query_hash: str) -> Any | None:
        composite_key = self._make_composite_key(session_id, query_hash)
        entry = self._store.get(composite_key)
        if entry is None:
            self._stats["misses"] += 1
            self._logger.debug("cache_miss_l1", session_id=session_id, query_hash=query_hash)
            return None

        inserted_at, entry_ttl, result = entry  # ← 解构三元组
        if time.monotonic() - inserted_at > entry_ttl:  # ← 使用条目级 TTL
            del self._store[composite_key]
            self._stats["expirations"] += 1
            self._logger.debug("cache_entry_expired", ...)
            self._stats["misses"] += 1
            return None

        self._store.move_to_end(composite_key)
        self._stats["hits"] += 1
        self._logger.debug("cache_hit_l1", ...)
        return result

五、方案二：写入时抽样主动过期清理（P1）

5.1 设计思路

参考 Redis active-expiration 双轨制（惰性删除 + 主动抽样），在写入路径上增加轻量级抽样清理：每 N 次写入随机抽样检查 20 条，移除已过期条目。

  • 零额外开销：不需要后台 asyncio Task、不需要定时器、空闲时零 CPU
  • 随流量自适应：高写入时清理更频繁，低流量时依赖惰性淘汰即可
  • 概率性覆盖：每次抽样 20 条，配合 LRU 自然淘汰，过期条目不会长期堆积

5.2 实现细节

# cache_manager.py

import random

class CacheManager:
    _CLEANUP_SAMPLE_SIZE = 20   # 每次抽样检查 20 条
    _CLEANUP_TRIGGER_EVERY_N = 10  # 每 10 次写入触发一次清理

    def __init__(self, ...):
        ...
        self._write_count = 0

    def _maybe_sweep(self) -> None:
        """写入时抽样清理过期条目（Redis active-expiration 模式）。"""
        self._write_count += 1
        if self._write_count % self._CLEANUP_TRIGGER_EVERY_N != 0:
            return
        self._sweep_expired(self._store, "l1")
        self._sweep_expired(self._l2_store, "l2")

    def _sweep_expired(self, store: OrderedDict, label: str) -> int:
        """随机抽样清理过期条目，返回清理数量。"""
        if not store:
            return 0

        keys = list(store.keys())
        if len(keys) <= self._CLEANUP_SAMPLE_SIZE:
            sample_keys = keys
        else:
            sample_keys = random.sample(keys, self._CLEANUP_SAMPLE_SIZE)

        now = time.monotonic()
        removed = 0
        for key in sample_keys:
            entry = store.get(key)
            if entry is None:
                continue
            inserted_at = entry[0]
            entry_ttl = entry[1] if len(entry) >= 3 else self._ttl  # 兼容旧二元组
            if now - inserted_at > entry_ttl:
                del store[key]
                removed += 1

        if removed:
            self._stats["sweep_removed"] += removed
            self._logger.debug(
                "cache_sweep_expired",
                label=label, removed=removed,
                sampled=len(sample_keys), total=len(store),
            )
        return removed

六、方案三：无匹配/零向量缓存策略优化（P0）

6.1 核心问题

当前 SearchService 对正常、无匹配、零向量三种结果一视同仁地缓存（相同 TTL、相同 LRU 队列）。

后果：

  • 10 分钟的无匹配缓存（固定短语"根据现有文档内容，无法回答此问题"）占用宝贵的缓存槽位
  • 当用户高频尝试不同查询（探索阶段），大量无匹配结果涌入缓存 → LRU 淘汰正常 LLM 生成结果
  • 零向量结果纯属知识库未初始化，缓存毫无意义

无匹配 ✅ 缓存 600s ❌ 不缓存 N/A
零向量 ✅ 缓存 600s ❌ 不缓存 N/A

七、方案四：缓存可观测性 —— 结构化日志（P1）

7.1 设计思路

不引入 Prometheus / OpenTelemetry 等重型依赖，不暴露 HTTP 管理端点。仅在 CacheManager 中维护统计计数器，通过结构化日志输出快照。

理由：项目无用户认证系统，暴露管理端点有安全风险；进程重启后内存统计归零，端点数据不可靠。主流 AI 框架（LangChain、LlamaIndex、GPTCache）均通过日志/回调输出缓存统计。

7.2 统计指标

指标类型说明
hitsCounterL1 缓存命中次数
missesCounterL1 缓存未命中次数
l2_hitsCounterL2 缓存命中次数
l2_missesCounterL2 缓存未命中次数
evictionsCounterLRU 淘汰次数
expirationsCounter惰性淘汰次数（TTL 过期）
sweep_removedCounter写入时抽样清理移除数（方案二）

l2_sizeGauge当前 L2 条目数（已有）
hit_rateGaugeL1 命中率 = hits / (hits + misses)

7.3 实现细节

# cache_manager.py

class CacheManager:
    _STATS_LOG_INTERVAL = 300.0  # 每 5 分钟输出一次统计快照

    def __init__(self, ...):
        ...
        self._stats = {
            "hits": 0, "misses": 0,
            "l2_hits": 0, "l2_misses": 0,
            "evictions": 0, "expirations": 0,
            "sweep_removed": 0,
        }
        self._last_stats_log = time.monotonic()

    def get_stats(self) -> dict:
        total = self._stats["hits"] + self._stats["misses"]
        return {
            **self._stats,
            "size": self.size,
            "l2_size": self.l2_size,
            "hit_rate": round(self._stats["hits"] / total, 4) if total > 0 else 0.0,
        }

    def _maybe_log_stats(self) -> None:
        """定期输出统计快照到结构化日志。"""
        now = time.monotonic()
        if now - self._last_stats_log >= self._STATS_LOG_INTERVAL:
            self._logger.info("cache_stats_snapshot", **self.get_stats())
            self._last_stats_log = now

十、文档重新索引后旧缓存处理分析

10.1 核心发现：无缓存失效机制

结论：上传新文档并完成重新索引后，旧的缓存答案和旧的 404/无匹配响应 不会被主动清除，仍会在 TTL 有效期内被命中返回。

10.2 缓存键构成分析

当前缓存键 不包含 任何知识库版本信息：

缓存层缓存键构成代码位置是否含版本号
SearchService L1 SHA-256(session_id + ":" + query + ":" + top_k)[:16] search.py:109-116 ❌ 否
QueryRewriter L1 session_id + ":" + query_hash cache_manager.py:236-241 ❌ 否
QueryRewriter L2 "l2:" + normalized_query cache_manager.py:244-250 ❌ 否

10.3 上传/索引管线与缓存的隔离

完全隔离 —— 无任何挂钩点

操作路由文件是否触发缓存失效
文件上传 (POST /api/uploads) uploads.py ❌ 否
文档解析 (POST /api/document-parsing-jobs) document_parsing.py ❌ 否
文档分块 (POST /api/document-chunk-jobs) document_chunking.py ❌ 否
向量化 (POST /api/document-embedding-jobs) document_embedding.py ❌ 否
重新向量化 (POST /.../re-embed) document_embedding.py:213 ❌ 否

上传和索引路由完全不了解缓存层的存在，反之亦然。CacheManager 提供的 clear() 方法（cache_manager.py:130）从未被任何生产代码调用。

10.4 具体影响场景

场景 A：旧答案被缓存后新文档索引完毕

  1. 用户在会话 sess_abc 中提问「公司的考勤制度是什么？」
  2. 知识库中无相关文档 → 返回 「根据现有文档内容，无法回答此问题」
  3. 该无匹配响应被缓存（TTL = 600s），Key = SHA-256("sess_abc:公司的考勤制度是什么？:5")
  4. 管理员上传《考勤制度 v2.0.pdf》并完成分块+向量化（10 秒后完成）
  5. 用户再次提问「公司的考勤制度是什么？」（距第一次 30 秒）
  6. 结果：命中缓存，返回旧的「无法回答」——即使知识库已有相关文档

场景 B：旧正常答案被缓存后知识库更新

  1. 用户提问「退换货政策是什么？」→ LLM 基于旧版《退换货政策 v1》生成回答 → 缓存 600s
  2. 管理员上传《退换货政策 v2》（规则已变更），完成重新索引
  3. 用户再次提问同一问题（缓存未过期）
  4. 结果：命中缓存，返回基于 v1 的旧回答，用户看到的是过时信息

场景 C：跨会话 L2 缓存的放大效应

  1. QueryRewriter L2 缓存的 TTL 高达 3600s（1 小时），且是跨会话共享的
  2. 用户 A 在会话中触发了某个改写，结果存入 L2（标记为 general_knowledge）
  3. 知识库更新后，用户 B 在完全不同的会话中提问
  4. 结果：用户 B 可能命中用户 A 的旧 L2 改写缓存（1 小时内），使用过时的改写结果进行搜索

10.5 进程重启的隐式"清理"

当前缓存为纯内存存储（OrderedDict），进程重启后所有缓存自动清空。这意味着：

  • ✅ 部署新版本 → 缓存自动清空（副作用变为特性）
  • ✅ 服务重启 → 缓存清零
  • ❌ 但这不是设计意图，而是内存存储的附带行为
  • ❌ 生产环境中服务可能长时间运行（数天/数周），依赖重启来清理缓存不可靠

10.7 推荐方案

方案 A（推荐，轻量）：缓存键加入知识库指纹

在 SearchService 缓存键中拼接知识库指纹（如所有 embedding 记录中 MAX(created_at) 的 hash），知识库有任何更新 → 指纹变化 → 所有旧缓存自动失效。

# search.py —— _make_search_cache_key 改进
@staticmethod
def _make_search_cache_key(session_id: str, query: str, top_k: int, kb_fingerprint: str = "") -> str:
    raw = f"{session_id}:{query}:{top_k}:{kb_fingerprint}"
    return hashlib.sha256(raw.encode()).hexdigest()[:16]

# 在 search() 方法开头计算指纹
kb_fingerprint = self._get_kb_fingerprint()  # SELECT MAX(updated_at) FROM document_embeddings

优点：零侵入性（不修改上传/索引路由）、自动失效、实施成本极低（3 行 SQL + 1 个字段）。

缺点：任何文档更新都会清空所有缓存（粒度较粗）。

方案 B（进阶，精细）：向量化完成后回调清除缓存

在 DocumentEmbeddingService.execute_queued_job() 成功完成后，发送一个信号/事件，由缓存层监听并选择性清除。

# 在 re-embed 成功后调用
from app.services.cache_manager import get_search_response_cache
cache = get_search_response_cache()
if cache:
    cache.clear()  # 清空所有 L1 + L2 缓存

优点：精确触发、即时生效、实现简单。

缺点：需要在索引路由中注入缓存依赖（DI 链变更）、clear 粒度粗（清空所有会话缓存）。

11.2 问题严重性分析

零向量场景的特殊危害

零向量响应（total_searched == 0）意味着知识库完全为空。这个状态的缓存是最危险的：

  1. 完全阻塞：一旦被缓存，用户在 10 分钟内无论如何都无法获得任何答案——即使管理员在此期间完成了文档上传+索引。
  2. 零价值缓存：返回的是 68 个字符的固定中文字符串，不涉及 LLM 调用，缓存它没有任何成本节省。
  3. API 层面已返回 404：路由层在检测到 total_searched == 0 时已经 raise HTTP 404（search.py 路由:321-325），但在此之前缓存已经写入。这意味着第二次请求会命中缓存返回 200 而非 404，行为不一致。

无匹配场景的问题

  1. 浪费 LRU 槽位：固定文本占用与 LLM 生成结果相同的内存和 LRU 位置。
  2. 阻塞新文档生效：与场景 A 相同——新文档索引后，旧的无匹配缓存仍会命中。
  3. 无 LLM 成本节省：_build_no_match_response 不调用 LLM（search.py:786-787），缓存它不节省任何 API 费用。

11.3 AI 项目最佳实践对比

框架/项目对空结果/无匹配的处理
LangChain 不缓存空结果；BaseCache 的 lookup 返回 None 时直接走 LLM 调用路径
GPTCache 默认不缓存空响应；可通过 cache_empty_result 配置项控制（默认 False）
LlamaIndex IngestionCache 不区分结果类型；查询结果缓存由用户自行实现，社区建议跳过空结果
RAG 最佳实践 空结果（无匹配/无数据）不应缓存：① 没有 LLM 成本需要节省；② 缓存空结果会阻止知识库更新后的正确回答；③ 空结果的响应体积极小，重新计算成本可忽略

十二、待确认问题（Q&A）

以下问题需要产品/业务方确认后决定实施方案

Q1：知识库更新后的缓存行为期望 ✅ 已确认

背景：当前缓存键不含知识库版本信息，重新索引后旧缓存继续生效（最长 10 分钟）。

确认答案：方案 A —— 知识库指纹

知识库更新后，所有用户的搜索缓存都应立即失效。通过知识库指纹（fingerprint）机制，文档上传完成 → 指纹变化 → 旧缓存自动失效，无需人工干预。

实施要点：

  • 缓存键中加入知识库指纹（如最新文档更新时间戳的哈希）
  • 文档重新索引完成后更新指纹 → 所有旧缓存键自动失效
  • 同时适用于 L1 和 L2 缓存（见 Q2）

Q2：L2 语义缓存（跨会话）是否需要加入知识库版本感知？ ✅ 已确认

背景：QueryRewriter L2 缓存 TTL = 3600s，跨会话共享。知识库更新后，其他用户可能命中旧的改写结果。

确认答案：需要 —— L2 也加入知识库指纹

L2 语义缓存虽然只缓存改写结果而非搜索答案，但知识库更新后术语映射、领域知识等都可能变化，旧改写结果已不适用。L2 同样需要知识库版本感知，与 L1 使用统一的指纹机制。

Q3：是否需要为管理员提供手动清除缓存的 API？ ✅ 已确认

背景：项目无用户认证系统（参见 D4），暴露管理端点有安全风险。但生产运维中可能需要手动清除缓存。

确认答案：方案 A —— 不需要

依赖 TTL 自动过期 + 知识库指纹自动失效即可。紧急情况通过进程重启清除内存缓存。与 D4 决策一致，与 LangChain/GPTCache/LlamaIndex 行业惯例对齐。

Q4：无匹配/零向量不缓存的决策确认 ✅ 已确认

背景：方案三（第六节）决策 D2 已确定「无匹配和零向量不缓存」。本节提供了详细的技术分析支持。

确认答案：不缓存，不做折中

无匹配（rows=0）、零向量（total_searched=0）、零数据均不缓存。不需要极短 TTL 折中方案——这些场景返回的是固定短语，无 LLM 调用成本，缓存价值为零。直接跳过缓存写入即可。
