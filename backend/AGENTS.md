# knowra 后端章程

## 1. 端侧定位

**knowra 后端** 是 knowra 的服务端与知识能力编排层，负责提供统一 API、管理数据与配置、承载文档处理、索引检索、模型服务适配、RAG 编排和后续知识图谱、评测能力的服务端边界。

后端不单独定义产品范围和业务优先级。产品目标、跨端边界和 OpenSpec 治理以根目录 `AGENTS.md` 为准；具体功能范围、验收标准和阶段任务以 OpenSpec 变更文档为准。

## 2. 技术栈基线

- **语言**：Python 3.14.5
- **Web 框架**：FastAPI
- **ASGI 服务**：Uvicorn，生产进程管理可使用 Gunicorn
- **ORM**：SQLModel
- **数据库**：PostgreSQL + pgvector
- **迁移**：Alembic
- **配置管理**：Pydantic Settings、`.env`、`.env.example`
- **测试**：pytest，必要时配合 `httpx` / FastAPI TestClient
- **格式化与静态检查**：ruff
- **包与命令管理**：uv

依赖版本以 `pyproject.toml` 和 `uv.lock` 为准。升级框架、数据库驱动、迁移工具或核心依赖时，应通过 OpenSpec 说明动机、影响范围和验证方式。

## 3. 后端职责

后端主要负责：

- FastAPI 应用入口、路由注册、中间件和生命周期管理。
- `/api` 前缀下的统一 HTTP API。
- 环境配置、日志、错误处理和跨域配置。
- PostgreSQL 数据访问、SQLModel 模型、Alembic 迁移和 pgvector 扩展。
- 邮箱密码认证、可撤销会话、账户资料与管理员角色管理；凭据独立存储。
- 文档解析、分块、元数据入库和索引构建的服务端流程。
- Embedding、重排、查询改写、HyDE、RAG 等模型相关能力的服务适配和编排。
- 检索服务、引用溯源、知识图谱和评测平台的后端扩展边界。

模型能力可以通过第三方平台、本地服务或后续可替换适配器接入。后端设计应关注接口抽象、配置隔离和可替换性，不应在章程层面预设唯一部署方式。

## 4. 推荐目录边界

后端代码应按 API、配置、数据、领域模型和服务逻辑分层。

```text
backend/app/
├── api/        # 路由、API 聚合与请求入口
├── core/       # 配置、日志、应用级基础设施
├── db/         # 数据库连接、session、初始化
├── models/     # SQLModel 数据模型
├── schemas/    # 请求/响应 schema
├── services/   # 业务服务、检索、文档处理、模型适配
├── cli.py      # 管理员初始化、旧账号认领与密码恢复
└── main.py     # FastAPI 应用入口
```

路由层应保持薄层，只负责参数接收、依赖注入和响应返回；业务流程应下沉到 `services/` 或更明确的领域模块。

## 5. API 与配置规范

- 所有业务接口必须挂载在 `/api` 前缀下。
- 跨端接口的请求体、响应体和错误语义应保持稳定；破坏性变化需要通过 OpenSpec 说明。
- 敏感信息不得硬编码，统一通过 `.env`、`.env.example` 和配置模块管理。
- 第三方模型平台的 API Key、Base URL、模型名、超时和重试策略应配置化。
- 数据库连接串、CORS 来源、调试开关等环境差异必须通过配置隔离。
- 新增数据库表、索引或扩展时应配套 Alembic 迁移。
- 除健康检查与认证入口外，路由统一挂载认证依赖；资料操作使用读写权限依赖，并校验资源所属用户。管理员不获得他人资料的读取权限。
- Cookie 会话仅保存令牌哈希；改密或禁用撤销全部会话。响应与日志不得包含密码、凭据哈希或会话令牌，校验错误也不得回显请求秘密。
- 检索、资料计数、指纹、缓存与请求去重必须使用已认证用户作用域；不得恢复默认用户旁路。
- 问答准入与后台额度增删共用按账号 UUID 稳定映射的 PostgreSQL 事务 advisory lock，再读取/锁定限额行，覆盖无行首次设限竞态；事务须先于昂贵依赖结束，不能跨网络持锁。失败及生成降级释放，超限返回 429 `chat_quota_exceeded` 与 `Retry-After`。调整额度保留未过期预留，不限额期间不追溯补记；占用不等同历史成功次数或账单。命令行密码只从隐藏交互或 stdin 读取。
- 后台用户生命周期和模型配置仅授予管理员；删除采用软删除并保留资料归属，重置/删除/禁用撤销会话，事务中重新校验操作者并保留至少一位有效管理员。
- 已接入审计的账号与模型写操作必须由统一审计事务边界提交，业务服务不得提前 commit；成功审计不可写时整体回滚并返回 `admin_audit_unavailable`。失败/拒绝在回滚后独立留痕，降级日志只含安全标识；密码、密钥、会话材料、显示名、完整地址和资料内容不得进入管理审计。
- 模型密钥通过独立环境主密钥加密，管理响应与日志不得包含明文或密文。模型使用路径读取用途绑定并建立独立快照，配置版本参与缓存与熔断隔离；客户端在请求或任务结束时关闭。
- Embedding 默认切换与任务入队共用绑定锁；存在有效向量或 queued/running 任务时不得改变地址、模型或维度，普通请求不得覆盖已选后台模型空间。
- `operations:read`、`audit:read` 仅授予管理员；总览与三阶段任务使用独立字段白名单，禁止读取或返回他人文件名、标题、路径、正文、chunk、向量、问答和原始错误。审计查询再次按动作白名单投影，不开放编辑、删除或导出。
- 模型诊断只接收已保存配置 ID 与期望 revision，使用固定非私有样例、请求内异步客户端、总截止时间与零重试；实际连接绑定经校验 DNS 结果，禁止元数据/链路本地目标和重定向。跨 worker 准入使用数据库短事务与租约，完成结果与审计原子提交；测试不激活配置。
- 系统状态的主动检查每项最多 2 秒、合计 5 秒；readiness 仅代表当前实例。生效配置单独读取，刷新不访问模型供应商；认证数据库失效时保留认证边界并返回安全依赖错误。

## 6. 服务设计规范

- 文档解析、分块、Embedding、检索、RAG、引用溯源等能力应通过清晰接口连接，避免互相写死。
- 服务层应优先表达业务流程，避免把第三方 SDK 调用散落在路由或模型中。
- 外部服务调用应封装在适配器或服务模块中，便于替换、测试和降级。
- 检索和生成链路应保留可观测信息，例如查询、召回片段、引用来源和错误原因。
- 数据模型和 API schema 应区分清楚，避免把数据库内部结构直接暴露为长期 API 契约。

## 7. 日志调用规范

后端业务代码必须通过 `from app.core.logging import get_logger` 获取项目 logger，并统一使用“固定事件消息 + 关键字参数结构化字段”的写法：

```python
logger.info("上传完成", file_name="notes.pdf", byte_size=2048)
```

动态值必须作为 keyword field 传入，保持 `event` 字段稳定且便于检索。禁止使用以下混用方式：

- `%s` / `%d` 等位置参数格式化，例如 `logger.info("上传完成: %s", file_name)`。
- f-string、`str.format()` 或字符串拼接把动态值写入日志消息。
- `extra={...}` 字典传递结构化字段。
- `print()`、原始 `logging.getLogger()`、`logging.basicConfig()` 或其他绕过项目日志系统的方式。

OpenSpec proposal、design、spec、tasks 或 README 中出现后端日志示例时，也必须使用同一写法。Code Review 和测试应拒绝上述禁止写法。

## 8. 质量门禁

后端变更完成前，应根据影响范围运行必要验证命令：

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

涉及数据库结构的改动，应验证 Alembic 迁移可执行。涉及 API 的改动，应至少覆盖状态码、响应结构和关键错误分支。涉及第三方模型服务的改动，应优先通过可替换配置、mock 或集成开关降低测试脆弱性。

## 9. 文档同步

以下变化需要同步更新文档：

- 启动方式、环境变量、端口、数据库或迁移流程变化。
- 后端目录结构或技术栈变化。
- API 路径、请求响应结构或错误语义变化。
- 文档处理、检索、模型适配、RAG 等核心服务边界变化。

同步目标通常包括 `backend/README.md`、根目录 `README.md`、相关 OpenSpec artifacts，以及必要时更新本章程。
